================================================================================
importantdocsneedkown 前置认知入口：全景地图、北极星与信息治理体系
================================================================================

【文档定位】
本文件是 `importantdocsneedkown` 目录的前置信息入口与治理总览。

代码库本身通常只能呈现“当前实现成了什么样”，却难以完整承载“为什么做成这样”“哪些
价值与边界构成项目的灵魂”“本地与线上真实的运行形态如何演进”，以及“历次迭代背后
的取舍与踩坑脉络”。`importantdocsneedkown` 目录正是为沉淀这些跨会话、跨阶段的长期
认知而设立的知识中枢。

阅读本目录的视角天然是多元的——可能来自产品思考、医学专业、界面设计、工程实现、
测试验收、项目主人回看，或不同阶段的 AI 智能体。因此，本文件专注于清晰、平实地呈递
目录格局、三颗效果北极星、建议阅读路径、信息运动规律、文档落笔心法与授权边界，供
不同背景的阅读者自然载入完整上下文。

================================================================================
一、三颗效果北极星：理解项目全局的根本坐标
================================================================================

本项目围绕产品价值、工程交付与知识治理的各类权衡，均可回溯到以下三颗彼此呼应的
**效果北极星**：

1. 【产品与医学价值北极星】—— 项目守护的人群与灵魂（完整宪章见《产品与医学价值北极星.txt》）
   **“立足香港糖尿病长者（‘老友记’）的真实生命处境，以生命与身心安全为底线，以循证医学与共同决策（SDM）为根基，做长者日常慢病自我管理与看诊前后的温暖协作者——不替代医生，不替长者做主，而是持续陪伴并赋能长者获得‘看得懂的循证信息、想得清的个人价值、带得进诊室的沟通底气’，从容走出最适合自己人生的控糖路。”**
   其下包含五条不随界面形态与技术演进而动摇的底层认知公理（安全与全人底线、循证与
   自主并重、看见真实个体与纵向理解、默认长者友好与母语共鸣，以及面向未来迭代的轻重
   序位），完整正文收录于《产品与医学价值北极星.txt》。

2. 【交付与发布北极星】—— 工程迭代平滑落地的核心效果
   **“让任何人从 Google AI Studio 下载迭代后的代码 ZIP 文件，到基于本地原有代码和环境重新启动/发布，所需踩的坑和要做的动作尽量少。”**
   这颗北极星根植于一个关键的工程现实：**项目在 Google AI Studio 中的运行形态，与本机及当前线上的真实运行形态并不相同**——
   - 在 Google AI Studio 中，运行环境需要单进程监听 3000 端口，因此由根目录的 `server.ts`（`npm run dev`）统一承接前后端；
   - 而在本机调试与当前线上运行中，实际流程**不走 `npm run build`**，而是以双进程直接启动：API 端运行 `npm run dev:api`（入口 `server/index.ts`，监听 `127.0.0.1:8787`，自动读取 `.env.server.local`），UI 端运行 `npm run dev:ui`（入口 `vite.config.ts`，监听 `127.0.0.1:5173`，将 `/api` 代理至 `8787`）。
   基于这一“双轨共存”的现实，Google AI Studio 侧的功能开发与平台适配以不破坏本机/线上双进程链路为前提；所有 AI 请求统一收口于后端 API 端，非必要不改动既有接口契约、端口代理、脚本与依赖，使“下载代码 → 同步回本地仓库 → 重启服务”保持尽可能平滑。

3. 【认知延续与信息治理北极星】—— 分层治理知识库的长期效果
   **“让任何一个毫无前序记忆的阅读者或智能体，读完本目录后，都能获得与前序阶段一致的信息量与认知水位；同时让目录内的信息长期保持真实、纯粹、自洽、不被噪音污染。”**
   知识库常见的两种失衡，一是“信息滞后”（代码变更了依赖、环境变量或后端接口，文档却停在旧状态），二是“边界失守”（把极稳定的底层价值与临床理论文档当成开发草稿随手涂改，或在阶段尚未定型时往历史归档里倾倒半成品流水账）。本目录的分层设计，旨在“诚实反映工程实况”与“稳妥守护稳定基石”之间建立清晰的秩序。

二、目录全景地图：六大组成部分的定位与分工
================================================================================

`importantdocsneedkown/` 下目前共有 6 个组成部分，按**“变化频率”与“认知层级”**自然分层：

--------------------------------------------------------------------------------
1. 《00_文档总索引与信息治理规范.txt》（本文件）
   【定位】前置入口地图 & 信息治理与落笔体系
--------------------------------------------------------------------------------
- 承载内容：整个 `importantdocsneedkown` 目录的全局鸟瞰图、三颗北极星、建议阅读路径、信息运动规律、文笔表达心法与授权边界。
- 置于 00 位的意义：作为进入目录的第一扇门，帮助刚接触本项目的阅读者先建立整体元认知，再按需深入各份具体文档。

--------------------------------------------------------------------------------
2. 《产品与医学价值北极星.txt》
   【定位】产品灵魂宪章 & 最高价值与轻重序位坐标（默认只读）
--------------------------------------------------------------------------------
- 承载内容：整个项目最本质、最泛化、不绑定于特定界面形态或单一功能模块的核心宣言与五大底层认知公理，涵盖安全与全人底线、SDM/PDA/ODSF/CCM 共同决策使命、香港老年医学与纵向个体化理解、健康素养普遍预防原则，以及未来一切迭代的恒定轻重序位。
- 与《核心业务明细》的关系：本文件立“纲”（呈递灵魂、方向与轻重序位），《核心业务明细》列“目”（沉淀具体临床业务规则、方法论细节与数据契约），一纲一目、互为表里。
- 只读属性：作为跨越版本与界面形态的定盘星，不随日常代码变动自动演进，仅在项目主人慎重思考并给出显式授权时进行修订。

--------------------------------------------------------------------------------
3. 《任何代码迭代变动者须知.txt》
   【定位】工程行动边界 & 交付北极星
--------------------------------------------------------------------------------
- 承载内容：项目在工程改动层面的两条核心共识：
  * 第一条关乎**动笔尺度**：思考、讨论、设想可以充分展开，真正落笔改动代码时则保持审慎与克制，聚焦最必要的最小改动，避免顺手重构或误伤无关业务逻辑、配置与注释；
  * 第二条关乎**交付北极星**：将“从 Google AI Studio 下载代码 ZIP 回到本地原有环境重新发布，踩坑最少、动作最少”落到对既有双进程链路（`vite.config.ts`、`dev:ui`、`dev:api`、`server/index.ts`、`.env.server.local`）的保护、对“所有 AI 请求收口于后端 API 端且契约稳定”的坚持，以及对依赖变更与文档自洽的克制。
- 独立成文的价值：简明直观，清晰界定工程层面的克制边界与交付锚点。

--------------------------------------------------------------------------------
4. 《本项目剥离UI后用于UI重构的核心业务明细.txt》
   【定位】底层核心业务逻辑与医学理论细则（默认只读基石）
--------------------------------------------------------------------------------
- 承载内容：与具体 UI 呈现和前端外壳解耦的底层临床业务与医学理论细则——包括目标人群特征、三支柱价值承诺、共同决策（SDM）、患者决策辅助（PDA）、ODSF、Elwyn 三阶段模型、动机式访谈（MI）、健康素养普遍预防原则（Health Literacy Universal Precautions）、慢病照护模型（CCM），以及 5-Node 推理、安全门控、问诊备忘、饮食/运动/用药/血糖管理等完整业务定义。
- 默认只读的原因：界面、组件与工程形态属于“快变量”，会随迭代不断变化；而这份文件所承载的临床理论框架、医疗伦理边界与核心业务骨架属于“极慢变量”。它不随日常代码改动、UI 翻新或工程适配自动迭代，以免严谨完整的医学设计被碎片化的实现记录稀释；仅在底层业务或医学模型本身确需演进、并获用户显式明确授权时进行修订。

--------------------------------------------------------------------------------
5. 《GoogleAIStudio迭代代码下载后本地重启服务指南.md》
   【定位】当前代码运行态实况 & 本地重启验收手册
--------------------------------------------------------------------------------
- 承载内容：专门面向“本地已有仓库曾成功启动过，现将 Google AI Studio 新代码同步应用后重新启动 UI 与 API 服务”这一场景的实战说明。完整记录双进程模式（`dev:api` 8787 + `dev:ui` 5173）与 AI Studio 单进程模式（`server.ts` 3000）的边界、`.env.server.local` 配置实况、后端 AI 接口基线（含 `/api/ai/transcribe`）、标准启停验收步骤与高频排查对照。
- 随工程现实同步的原因：这份手册直接服务于交付北极星。当代码变动确实改变了启动条件、依赖版本、环境变量或后端接口基线时，手册随之诚实更新，使实际运行态与文档保持严丝合缝；若改动未影响运行条件，则无需扰动。

--------------------------------------------------------------------------------
6. 《历史迭代阶段/》（文件夹）
   【定位】跨会话演进记忆归档库（按阶段显式授权封存）
--------------------------------------------------------------------------------
- 承载内容：历次迭代阶段收口后，经用户显式授权沉淀下来的完整阶段历史文档（每个阶段 1 份 `.txt` 文件，文件名包含精确到分钟的时间戳以及词素充沛、全局唯一的阶段指代名）。
- 封存机制背后的考量：单次会话中常包含大量探索、试错与推翻重来，何时真正定型、哪些脉络适合沉淀进长期记忆，由项目主人拍板确认。等待显式授权能够确保目录中的每一份归档都是高信噪比、已定案的认知快照；归档生成后原则上保持只读，后续新认识或纠偏在之后获授权的新阶段文件中延续陈述。

    代理域名、旧 CDN 样式说明等）。阅读时可将两层信息自然分开看待：

四、信息运动规律、授权边界与落笔心法
================================================================================

健康的知识库有清晰的信息流动路径、明确的演进权限边界，以及一以贯之的书写气质。

1. 信息的四向自然流动
   - 【工程实况向上游同步】：当代码改动确实影响了本地或线上的运行条件（例如增删或升级 `package.json` 依赖、新增或调整环境变量、变动后端 `/api/ai/*` 接口基线、改变启停或排错路径），相关实况顺势同步至 `.env.example` 与《GoogleAIStudio迭代代码下载后本地重启服务指南.md》，保持文档与运行态一致。
   - 【阶段脉络向时间轴归档】：一轮迭代在充分讨论、落地并验证收口后，期间积累的背景、认知转折、取舍理由与全量变更脉络，在**获得用户显式授权后**，以充沛平实的陈述沉淀进《历史迭代阶段/》的新 `.txt` 文件，实现无损的跨阶段记忆交接。
   - 【核心基石保持静水流深】：《产品与医学价值北极星.txt》、《本项目剥离UI后用于UI重构的核心业务明细.txt》与《任何代码迭代变动者须知.txt》承载项目灵魂、底层临床理论与最高工程共识，默认以只读心态守护，不随日常开发流动而漂移，仅在项目主人经慎重考虑并给出显式授权时进行精准迭代。
   - 【入口地图随目录拓扑校准】：当 `importantdocsneedkown/` 根目录新增、删减、重命名文档，或信息治理共识本身演进时，顺势校准本入口文件（《00_文档总索引与信息治理规范.txt》）。而在 `历史迭代阶段/` 内按既有机制新增阶段归档时，本入口文件无需反复改动。

2. 授权边界的底层逻辑
   - **需要等待用户显式授权的变更**：
     * 迭代《产品与医学价值北极星.txt》——关乎项目最根本的灵魂宪章与长期价值坐标，天然只读、慎重演进；
     * 修订《本项目剥离UI后用于UI重构的核心业务明细.txt》——关乎底层临床理论与长期只读的业务基石；
     * 在《历史迭代阶段/》中新增归档文档——何时收口定型、将哪段演进封存入长期记忆，由项目主人判断；且已归档文件保持只读，后续新认知在新的获授权阶段文件中延续陈述；
     * 修订《任何代码迭代变动者须知.txt》——关乎项目主人立下的工程协作边界与交付北极星。
     *(若在协作过程中观察到某个阶段已适合归档，或发现只读基石文档存在值得探讨的演进空间，适合在对话中坦诚呈递观察与建议，待主人明确授权后再落笔，而非先斩后奏。)*
   - **属于工程自洽维护的同步变更（保持克制、精准）**：
     * 当代码变更切实改变了本地启动依赖、环境变量、端口代理或后端 API 接口基线时，顺势同步 `.env.example` 与《GoogleAIStudio迭代代码下载后本地重启服务指南.md》，并在沟通中清晰说明同步内容；若代码变动未触及运行条件，则不必多余触碰。

3. 文档落笔与表达心法（信息呈递、无角色喊话、认知传递）
   `importantdocsneedkown/` 下的一切文字沉淀，背后都贯穿着一套统一的表达哲学：

   - **不预设单一阅读者角色，不对特定角色喊话**
     本目录面向的阅读者丰富多样——可能是产品思考者、医学背景人士、设计师、代码开发者、
     测试与运维人员、未来的项目主人本人，或不同场景下接入的 AI 智能体，远远不只代码
     开发者一类。如果文档在落笔时预先假定对面只坐着某一种角色，频繁使用“致某角色”
     “请开发者注意”“你应该这样做”之类的喊话口吻，既会让其他视角的阅读者产生疏离感，
     也会把文档异化为“指挥某个特定岗位干活的工单”。
     因此，文档的重心始终放在**信息本身的清晰陈列与诚实呈递**上——把事实、背景、因果、
     边界与价值坐标干净透彻地摆在台面上，让任何身份的阅读者都能平等地读懂全貌，并结合
     各自的角色自然吸收运用。

   - **以“信息陈列呈递 + 妥帖的认知传递”为主，避免过重的指令感**
     这也是本目录天然排斥强硬指令式表达的深层原因：动辄使用“必须、一定、严禁、绝对
     禁止、切勿”等命令措辞，本质上是在居高临下地指挥特定执行者，既容易带来生硬的压迫感，
     又只能机械框住纸面上枚举出的有限条文，一旦遇到条文之外的新情境便会失灵。
     相比之下，把**客观信息陈列清楚**，并在涉及原则、灵魂与治理之处**自然合理地运用
     认知传递型表达**——讲透背后的真实处境、临床与人性逻辑、工程因果以及北极星指向——
     能够让阅读者在真正理解之后，自发认同并守住核心边界，哪怕置身从未写明的新变化中，
     也能循着底层认知自然推导出最妥帖的做法。

   - **不同文档类型的自然语体光谱**
     认知传递并非要求每份文档都长篇阐发道理，而是根据文档所承载信息的性质自然调配：
     * **前置入口与产品北极星（《00_文档总索引与信息治理规范.txt》《产品与医学价值北极星.txt》）**：
       以**信息清晰呈递 + 认知传递**为主，讲清全局格局、缘起、临床灵魂、治理初衷与轻重
       序位，语气温和笃定，靠道理本身的穿透力与清晰度凝聚共识；
     * **历史迭代阶段文档（《历史迭代阶段/*.txt》）**：
       以**客观、平实的陈述式信息陈列**为主，不带说教与指令感，完整忠实地陈述该阶段的
       起点、认知转折、方案权衡、逐文件变动、验证结果与现状边界，让后续无记忆的阅读者
       透过充沛的事实与脉络自然接续判断力；
     * **工程须知与重启指南（《任何代码迭代变动者须知.txt》《GoogleAIStudio迭代代码下载后本地重启服务指南.md》）**：
       清晰、克制、实事求是，把交付北极星、真实运行条件与排查线索透明摊开，让工程因果
       与踩坑成本自己说明分量。

   - **落笔后的温和自检视角**
     完成一段文档书写后，可以从两个朴素的视角回看：这段文字是在“把信息与底层认知清晰
     呈递出来”，还是在“对着某个假想角色发号施令”？拿掉“致某角色/你应当”的喊话与
     “必须/一定/严禁”的指令感之后，事实、因果与北极星本身是否依然清澈有力？当道理与
     信息自身就能稳稳立住时，文字往往就落在了最自然妥帖的分寸上。

4. 阶段历史文档的沉淀特征（获用户显式授权后）
   - **命名约定**：采用精确到分钟的时间戳 + 信息充分、词素不吝啬、能够唯一指代本阶段的阶段名，格式为：
     `<YYYYMMDD-HHMM>_<高区分度阶段指代名>.txt`
     （不以牺牲辨识度换取简短，使后人仅凭文件名即可直观区分各个阶段的核心脉络。）
   - **信息水位与语态**：以平实、客观、无指令感的陈述式信息陈列，完整交接本阶段的起因与目标、关键认知转折、取舍依据、逐文件变动与零改动范围、运行验证结果及当前边界。衡量信息是否充沛的核心参照只有一条：**假设阅读者毫无前序记忆，仅凭这份文档，是否就能还原与当时一致的信息量与判断水位。**

================================================================================
五、面对文档未覆盖的新情境：循北极星推导的典型范例
================================================================================

文档无法穷尽未来所有的具体场景。遇到未曾明文提及的新情况时，回溯三颗北极星与客观
工程/临床因果，通常都能自然推导出稳妥的取舍方向：

- 情境 1：Google AI Studio 预览环境的运行要求，与本地 `dev:ui`/`dev:api` 的原始配置出现冲突
  对照【交付与发布北极星】与双轨运行现实：将 AI Studio 平台特有的适配隔离在专用入口
  （如 `server.ts`）内，尽量保持 `vite.config.ts`、`server/index.ts`、`package.json`
  既有脚本及 `.env.server.local` 约定原封不动，往往能兼顾两头顺畅运行与本地零踩坑。

- 情境 2：审阅既有代码时产生顺手重构或顺手升级依赖的想法
  结合动笔克制原则与交付北极星衡量两件事：该改动是否为当前目标真正必要？改动是否会
  给本地下载重启增添额外的排查、报错或环境动作？若不能带来明确且必要的产品或交付收益，
  保持克制、减少扰动通常更具长期价值。

- 情境 3：新增 AI 能力时，面临前后端归属与环境变量配置选择
  对照【交付与发布北极星】与“AI 请求统一放后端 API 端”的既有架构共识：新 AI 能力
  自然落在 `server/app.ts` 与 `server/providers.ts` 体系下，使 `server/index.ts`
  （`dev:api`）与 `server.ts`（AI Studio）同步受益；新增环境变量兼顾行内 `#` 注释与
  空白清洗、提供合理回退，并如实同步至 `.env.example` 与《本地重启服务指南》。

- 情境 4：涉及面向香港糖尿病长者的功能设计、对话提示、健康建议、照护协同或界面表达
  对照《产品与医学价值北极星.txt》的五大底层认知公理与轻重序位（生命与身心安全 ＞
  临床伦理边界与患者自主权 ＞ 长者可理解性与真实生活贴合度 ＞ 界面精致度与技术巧思），
  再结合《核心业务明细》核对具体细则：是否守住了不诊断、不改药、不出处方、不保证的
  边界；在偏好敏感抉择中是否先同理并澄清价值、未提前锚定方案；是否贴合香港老年医学
  与地道粤语的低认知负荷表达。

- 情境 5：《核心业务明细》中的早期技术注记与当前仓库实现不一致
  结合文档的历史来源分层辨别：早期技术栈与直连代理等注记属于原项目的历史工程背景，
  当前工程实现以真实代码库与《本地重启服务指南》为准，《核心业务明细》本身无需为此
  顺手改写；若观察到底层临床业务逻辑确有值得演进之处，在对话中清晰呈递观察，等待
  项目主人显式授权后再作修订。
