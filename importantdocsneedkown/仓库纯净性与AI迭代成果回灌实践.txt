适用环境：macOS

## 阅读导航

本文档分为三个层次：

- 第 0–2 节：理解这套实践的由来、北极星与仓库边界；
- 第 3–5 节：按顺序执行出站、入站、验证与合并；
- 第 6–8 节：回滚、检查清单与附录。

若需要马上执行一次完整回灌，可以直接从第 4 节的变量与目录准备开始，再按第 5 节的顺序推进。最小执行路径是：

```
记录 base → 生成干净快照 → 解压导出物 → 建立候选 worktree → 排除叠加 → 分类评审 → 验证 → squash 合并 → 人工推送
```

## 0. 由来、背景与北极星群矩阵

### 0.1 这份文档要解决的问题

`tangyou_uistan` 是一个长期维护的项目。它既包含源码，也包含知识库、配置契约与人工发布口径。它会被不同的人手工维护，也会被不同的 AI 编程工具临时拿去迭代。每次 AI 工具迭代完成后，都会产生一份导出物；导出物里可能包含项目真正需要的改动，也可能包含工具元数据、IDE 元数据、包管理器产物、旧基线残留与未知文件。

这份文档讨论的是：如何让这些导出物经过一条清晰的回灌路径进入仓库，使仓库始终是一份纯净、可被人直接接手、可被任意 AI 工具替换迭代、且每次回流都可追溯可回退的权威基线。

### 0.2 原始意图与背景来由

旧的工作流通过“把 `.git`、`node_modules`、`.env.*` 等移出仓库，再叠加导出物，再移回”的方式保护本地专属物。这个动作的本质是**物理隔离**：通过暂时移走不可再生、不可被工具触碰的东西，避免它们在批量同步中被删除或篡改。

这份文档保留那个意图，但把保护方式从“物理移走”升级为“构造性隔离”：

- 交给 AI 工具的是干净快照，工具从一开始就看不到本地专属物；
- 导出物先进入仓库外的归档与候选工作区，不直接叠加到活仓库；
- 用 base、导出物与当前仓库做三方对比，推导工具真正想改什么；
- 只把经过分类与评审的变更应用到候选区；
- 验证通过后，由人把一次迭代处理为主分支上的一个提交。

这套实践追求的不是“消灭所有噪音”，而是让仓库始终停留在健康的张力区域：足够纯净，但不因流程过重而无法持续；足够开放，但不因工具而失去人的最终主权。

### 0.3 北极星群矩阵：七颗方向性北极星

北极星不是验收项，也不是可以一次性达成的状态。它是持续看向、不断逼近、但永远无法完全抵达的方向。七颗北极星共同构成一个张力空间；实践的目标不是最大化某一颗，而是让系统始终停留在“没有哪一颗塌陷”的区域。

| 北极星方向 | 磐石理由 | 不可达性 | 主要张力 |
| --- | --- | --- | --- |
| **走向语义自足** | 仓库是语义载体；一个文件若只能由某个工具或某台机器解释，它就不再属于项目本身。 | 新工具、新环境会不断带来新产物，边界需要持续重画。 | 与低摩擦冲突：分类与排除需要注意力。 |
| **走向人的可接手性** | 项目需要能在任何工具、厂商、智能体消失后，仍由一个人理解、运行、维护、发布。 | 隐性知识与上下文永远存在，文档只能不断逼近完整。 | 与 AI 加速冲突：工具可能带来不透明依赖。 |
| **走向工具可替换性** | AI 工具是临时的，项目是长期的；任何工具假设都会成为未来的负债。 | 工具各有独特能力，完全无锁定不现实。 | 与工具特定优化冲突：便利与可移植之间存在取舍。 |
| **走向可复现性** | 若不能从仓库加文档重建项目，仓库就不是权威来源。 | 环境漂移、依赖变化、外部服务差异永远存在。 | 与便利性冲突：提交生成物能省事，但破坏复现。 |
| **走向可逆性** | 不可逆的变更会让实验变成赌博，让 AI 加速失去安全网。 | 上下文会丢失，完美回退不可能。 | 与速度冲突：记录 base、评审 diff 需要时间。 |
| **走向人的最终主权** | 项目承载临床、伦理与发布责任，最终决定权不能外包给工具。 | 人也依赖工具与启发式，完全理性决策不可能。 | 与自动化冲突：全自动更快，但失去把关。 |
| **走向可持续的低摩擦**（约束性） | 一个没人愿意执行的完美流程，劣于一个能被持续使用的好流程。 | 摩擦不可能归零，只能在关键节点加码。 | 与纯净性、可追溯性冲突：重流程容易被绕过。 |

### 0.4 张力空间与导航原则

把“纯净 / 开放”作为横轴，“人的判断 / 机器自动化”作为纵轴，可以得到一个张力空间：

```
                    人的判断
                       ↑
    [纯净 · 判断]       |       [开放 · 判断]
    受保护文件评审       |       工具实验、方案探索
    删除候选确认         |       新工具试跑
    未知文件分类         |
    --------------------+--------------------→ 开放 / 可替换
    [纯净 · 自动]       |       [开放 · 自动]
    lint / build        |       AI 批量生成
    清单 / diff         |       草稿迭代
    分类 / dry-run      |
                       ↓
                    机器自动化
```

权威仓库尽量停留在左上象限：纯净，且由人做最终判断。AI 迭代发生在右下象限：开放、自动化、允许试错。机械检查位于左下象限，用来把人的注意力从搬运中解放出来。右上象限用于探索性工作，但成果需要经过左上象限的评审才能进入仓库。

导航原则可以概括为三句话：

- 机械动作尽量自动化，判断动作留给人；
- 未知文件默认不进入仓库，先进入归档与隔离区；
- 一次迭代在主分支形成一个提交，细节留在渠道归档。

### 0.5 北极星与实践的对应

| 北极星方向 | 对应实践 |
| --- | --- |
| 走向语义自足 | 归属 × 时间性矩阵、四类文件、默认拒绝、工具产物登记表 |
| 走向人的可接手性 | 受保护基线、干净 clone 测试、人工发布手册 |
| 走向工具可替换性 | 干净出站快照、渠道归档、工具产物外置 |
| 走向可复现性 | `npm ci`、lockfile、`.nvmrc`、干净 clone 测试 |
| 走向可逆性 | base 记录、候选 worktree、squash 提交、回滚表 |
| 走向人的最终主权 | 人工评审、人工 push、删除候选确认、未知文件隔离 |
| 走向可持续的低摩擦 | 分级验证、机械清单、按风险加码 |

## 2. 仓库边界与文件分类

### 2.1 归属 × 时间性矩阵

| | **项目内在** | **工具 / 环境特有** |
| --- | --- | --- |
| **持久** | **主仓库**：源码、文档、配置模板、发布手册、知识库 | **渠道归档中的工具资料**：`AGENTS.md`、工具指令、工具配置模板 |
| **临时** | **排除**：`dist/`、`.vite/`、`.wrangler/`、`verify-results/`、构建缓存、测试快照 | **排除 / 隔离**：`bun.lock`、`.idea/`、`.vscode/`、`.DS_Store`、工具缓存 |

这张矩阵不依赖某个工具的名字，也不依赖某次迭代的具体文件。新工具带来的新产物，可以先按“归属 × 时间性”判断，再进入工具产物登记表。

### 2.2 四类文件

| 类别 | 例子 | 处置 |
| --- | --- | --- |
| **本地专属、永不导入** | `.git`、`node_modules`、`.env`、`.env.local`、`.env.server.local`、`.dev.vars`、`.wrangler/`、`.idea`、`.vscode`、`.npmrc`、`.DS_Store`、`__MACOSX` | 出站不提供；入站按路径排除；不进入候选区 |
| **项目内在、但受保护** | `package.json`、`package-lock.json`、`.nvmrc`、`.env.example`、`.gitignore`、`vite.config.ts`、`server.ts`、`wrangler.jsonc`、`metadata.json`、`index.html`、`public/styles/`（`app.css` 及其 @import 的分文件）、`public/_headers`、`views/ConsultView/consultText.ts`、`domain/options.ts`、`tsconfig.json`、`importantdocsneedkown/` | 入站显示 diff，由人显式决定接受、回绝或部分合并 |
| **工具产物、默认拒绝** | `bun.lock`、`bun.lockb`、`AGENTS.md`、`.aider*`、`.cursor*`、`.claude/`、`.windsurf/`、`.continue/`、`.github/copilot-instructions.md` | 出站不提供；入站排除或归档到渠道目录 |
| **未知文件** | 新工具带来的新文件 | 进入渠道目录的 `unknown/`，人工分类后再决定 |

### 2.3 `.git`、`.idea`、`node_modules` 的处置

**`.git`**

- 出站使用 `git archive`，`.git` 天然不进入快照。
- 入站使用 `git worktree`，候选区的 `.git` 是一个指向主仓库 `.git/worktrees/...` 的文件，不是主仓库 `.git` 目录的副本。
- `rsync` 的排除清单包含 `.git`，工具导出物里即使出现 `.git`，也不会被叠加到候选区。
- 主仓库的 `.git` 从头到尾没有被移动、覆盖或删除。

**`.idea`**

- 当前 `.idea` 未被 Git 跟踪，属于本地 IDE 专属物。
- 出站快照不包含它；入站排除清单也排除它。
- 新流程不向活仓库写入，所以活仓库里的 `.idea` 不会被触碰。
- 工具导出物里如果出现 `.idea`，默认不进入 `export_full/`，也不进入候选区；如确有需要，可以在渠道归档中保留一份。

**`node_modules`**

- 出站快照不包含它。
- 入站排除清单排除它；候选区通过 `npm ci` 重新安装。
- `export_full/` 默认不保留 `node_modules`，因为它是可复现目录；原始 zip 作为完整证据保留。

### 2.4 工具产物登记表

| 产物 | 来源示例 | 处置 |
| --- | --- | --- |

## 3. 迭代渠道归档

### 3.1 归档根目录与渠道命名

归档根目录：

```
/Users/davie/Desktop/scrapt/tangyou_uistan/iteration_channels/
```

每个来源一个渠道目录，例如：

```
iteration_channels/
  GoogleStudio171账号/
  GoogleStudio另一个账号/
  程序员Tony/
  ClaudeCodeMac/
```

每次导入在渠道目录下再建一个时间戳子目录：

```
iteration_channels/
  GoogleStudio171账号/
    20261125-153045/
```

时间戳精确到秒，避免同一分钟内多次导入造成目录重名。

### 3.2 单次导入的目录结构

```
<渠道>/<时间戳>/
  export_original.zip     # 工具给的原始 zip，完整证据
  export_full/            # 解压树；默认排除 .git、node_modules、.idea、.env*、构建缓存
  excluded/               # 可选：被排除文件，保持原树
  tool_artifacts/         # 可选：已识别工具产物，保持原树
  unknown/                # 可选：未知文件，保持原树
  base_commit.txt
  base_snapshot.zip       # 可选：交给工具时的干净快照
  export_manifest.txt
  import_manifest.txt
  change_summary.txt
```

`excluded/` 是可选视图；不生成也不影响主流程。`export_full/` 与原始 zip 已经保留了完整证据。

### 3.3 原始 zip、export_full 与分类视图

- `export_original.zip`：工具给的原始 zip，完整证据；即使其中包含 `.env.local` 或其他敏感文件，也保持原样，因此渠道目录应视为敏感目录。
- `export_full/`：方便查看的解压树，默认省略 `.git`、`node_modules`、`.idea`、`.env*` 与可复现构建目录。
- `tool_artifacts/`、`unknown/`：分类视图，保持原始目录树，便于回看与找回。

### 3.4 base 与 import manifest

`base_commit.txt` 记录交给 AI 工具时的仓库 commit。`base` 应与实际交给工具的代码一致；若工具使用的是另一个快照，记录那个快照对应的 commit。

`import_manifest.txt` 记录本次导入的来源与起点：

```
channel: GoogleStudio171账号
base_commit: <hash>
base_branch: main
clean_snapshot: base_snapshot.zip
export_zip: export_original.zip
started_at: 2026-11-25T15:30:45+08:00
notes: 本次迭代的主要意图
```

这些是元数据，不是历史叙事。它们让后续可以做三方对比：

- base vs 导出物：工具真正改了什么；
- base vs 当前仓库：工具工作期间你改了什么；
- 当前仓库 vs 导出物：如果直接叠加会发生什么。

## 4. 出站：交给 AI 工具之前的干净快照

### 4.1 为什么需要干净快照

如果直接把工作目录打包给 AI 工具，`.env.local`、`node_modules`、`.idea`、IDE 元数据、构建缓存都可能被带进去。工具返回的导出物里就可能出现这些文件，后续需要额外排除。更稳的方式是：交给工具一份只包含项目内在文件的干净快照。

`git archive` 只打包已跟踪文件，天然不带 `.git`、`node_modules`、`.idea` 与本地 env 文件。这是交给 AI 工具的理想起点。

### 4.2 变量与目录准备

```bash
REPO="/Users/davie/Desktop/EffLearn/tangyou_uistan"
DESK="/Users/davie/Desktop"
ZIP="$DESK/tangyou_uistan.zip"
EXPORT="$DESK/tangyou_uistan"

ARCHIVE_ROOT="/Users/davie/Desktop/scrapt/tangyou_uistan/iteration_channels"
CHANNEL="GoogleStudio171账号"
STAMP="$(date +%Y%m%d-%H%M%S)"
CHANNEL_DIR="$ARCHIVE_ROOT/$CHANNEL/$STAMP"

STAGE="/tmp/tangyou_uistan_import"
BASE_WT="/tmp/tangyou_uistan_base_wt"
CAND_WT="/tmp/tangyou_uistan_candidate_wt"
CLEAN_CLONE="/tmp/tangyou_uistan_clean_clone"

mkdir -p "$CHANNEL_DIR"
chmod 700 "$CHANNEL_DIR"
```

### 4.3 预检与 base 记录

```bash
cd "$REPO"
git status --porcelain
git rev-parse HEAD | tee "$CHANNEL_DIR/base_commit.txt"
git archive --format=zip \
  --output="$CHANNEL_DIR/base_snapshot.zip" HEAD
```

预期：`git status --porcelain` 无输出；`base_commit.txt` 记录当前 commit；`base_snapshot.zip` 是只包含已跟踪文件的干净快照。

若工作区不干净，可以先 commit 或 stash，再记录 base；否则 base 与实际交给工具的代码可能不一致。

### 4.4 工具说明文件的放置

如果某个 AI 工具需要 `AGENTS.md`、工具指令或配置模板，可以放在渠道目录下的 `tool_artifacts/`，或工具自己的工作区里，不放入主仓库快照。

## 5. 入站：从导出物到候选工作区

### 5.1 总体流程

```
解压导出物
  → 归档原始 zip 与解压树
  → 建立 base worktree
  → 预览导出物相对 base 的变化
  → 建立候选 worktree
  → 叠加导出物（带排除）
  → 工具产物清扫
  → 未知文件隔离
  → 受保护基线评审
  → 删除候选评审
  → 候选区验证
  → 提交候选
  → 干净 clone 测试
  → squash 合并
  → 人工推送
```

`git worktree` 会在另一个目录创建一个共享同一 `.git` 的工作区；它不是 clone，不复制 `.git` 目录。候选区失败时删除即可，不影响主工作区。

### 5.2 解压与归档

```bash
rm -rf "$STAGE" "$EXPORT"
mkdir -p "$STAGE" "$EXPORT"
ditto -x -k "$ZIP" "$EXPORT"

find "$EXPORT" -name '.DS_Store' -delete
find "$EXPORT" -name '__MACOSX' -type d -prune -exec rm -rf {} +

test -f "$EXPORT/package.json" && echo "导出根目录 OK" || echo "检查导出根目录"
```

若 `package.json` 不在 `$EXPORT` 根目录，需要把 `EXPORT` 指向实际项目根。

rsync -a \
  --exclude='.git' \
  --exclude='node_modules/' \
  --exclude='.idea/' \
  --exclude='.env' \
  --exclude='.env.local' \
  --exclude='.env.server.local' \

  --exclude='dist/' \
  --exclude='.vite/' \
  --exclude='verify-results/' \
  --exclude='.next/' \
  --exclude='.turbo/' \

### 5.9 受保护基线评审

```bash
cat > "$STAGE/protected.txt" <<'EOF'
package.json
package-lock.json
.nvmrc
.env.example
.gitignore
vite.config.ts
server.ts
wrangler.jsonc
metadata.json
index.html
public/styles
public/_headers
views/ConsultView/consultText.ts
domain/options.ts
tsconfig.json
importantdocsneedkown
EOF

cd "$CAND_WT"
: > "$STAGE/protected_changed.txt"
while IFS= read -r p; do
  [ -z "$p" ] && continue
  if git diff --name-only HEAD -- "$p" | grep -q .; then
    echo "$p" | tee -a "$STAGE/protected_changed.txt"
    git diff HEAD -- "$p"
  fi
done < "$STAGE/protected.txt"
```

对每个受保护文件做决定：

- 保留工具改动；
- 回滚到 HEAD：`git checkout HEAD -- package.json`；
- 部分合并：手动编辑后 `git add`。

评审 `index.html` 时，一并查看 Tailwind CDN 之后是否仍保留：

```html
<link rel="stylesheet" href="%BASE_URL%styles/app.css">
```

若导出物删掉了这一行、把样式重新内联进 `index.html`，或改写了 `public/styles/` 下的入口与分文件，需要显式判断，而不是当作无关清理。这组样式表是页面皮肤与大字规则的现行位置。

`index.html` 的 `<head>` 里还有一组 preconnect / preload（字体、`public/styles/` 各分文件、首页插画），只让同一批地址提前并行下载。它们被删或改动时同样值得判断；同时核对 preload 中的分文件与 `app.css` 的 @import 列表是否一致——不一致不会让样式出错，但会让漏列的文件晚一步下载。

`public/_headers` 决定 Cloudflare Workers 生产环境的静态资源缓存（带哈希的 `/assets/*` 长缓存，`/art/*`、`/icons/*` 一天，`index.html` 与 `/styles/*` 每次再验证）。导出物改写或删除它，会直接改变线上用户何时拿到新版本，属于需要人显式决定的改动；规则含义见《线上无服务器部署实例（Cloudflare Workers）.txt》第 5 节。

`public/styles/app.css` 是样式入口，只含字体引入与按层叠顺序排列的 `@import`，各分文件（`public/styles/*.css`）承载具体规则；实际列表与顺序以 `app.css` 为准。`.large-font` 根规则与 `.ds-control` 是大字机制的组成部分。评审导出物对样式的改动时，重点看：@import 是否被删或调换顺序、被引用的分文件是否缺失、整块视图样式是否被删。核对 @import 列表：

```bash
grep -n '@import' public/styles/app.css
ls public/styles/
```

上述任何一种变化都不属于正常的导出差异。`views/ConsultView/consultText.ts` 保存发给 AI 的前端文本（欢迎语、快捷提问、偏好提交模板等），改动会直接改变送给模型的内容，同样需要显式决定。`domain/options.ts` 集中存放会被存储或送进 AI 的选项值（饮食习惯、运动天数/时长/强度、糖尿病类型、性别等），各页面只引用它；其中的取值一旦改动，新写入 `dia_profile` 的值与发给模型的档案摘要随之改变，已存的旧值也可能对不上新选项，因此与 `consultText.ts` 同属受保护基线，变化同样需要显式决定。

### 5.10 删除候选评审

```bash
grep -E '^\*deleting' "$STAGE/export_vs_base.txt" || true
```

逐项判断：

- 工具本意删除 → 在候选区显式删除：`rm -f "$CAND_WT/<path>"`；
- 工具没看见 → 保留；
- 基线漂移 → 重新基于最新快照迭代，或手动摘取真实改动。

若导出物明显缺少大量未触碰文件，删除候选多为噪声，不据此删除。

导出物给出 `*deleting` 时，任何当前仓库已跟踪的路径都值得停下来看一眼，其中分量较重的几类是：`public/`（`styles/*.css`、`art/`（页面插画 webp，二进制文件在导出物里尤其容易缺席）、`manifest.webmanifest`、`icons/`、`_headers` 等静态资源）、`components/` 与 `views/` 下的源码目录（含 `components/ui/`、`components/shell/`、各视图的分文件——如 `views/GlucoseView/sections/`、`views/MeView/`——与 `views/ConsultView/consultText.ts`）、`domain/`、`scripts/verify/`（含 `fixtures/golden/`）、`.env.example`、`server/`、`cloudflare/`、`wrangler.jsonc`。AI Studio 的导出物常常只是没有看见近期新增或拆分出的文件，所以对已跟踪路径的删除默认更接近“工具没看见”，予以保留，除非能说明这是有意删除；某一轮具体新增了哪些文件，可在《历史迭代阶段/》对应归档中查到。

### 5.11 候选区验证

```bash
cd "$CAND_WT"
npm ci --prefer-offline --no-audit --no-fund
npm run lint
npm run build
```

`npm ci` 严格按 `package-lock.json` 安装；若 lockfile 与 `package.json` 不同步，`npm ci` 会失败，此时可以改用 `npm install`，并把 `package-lock.json` 作为受保护文件重新评审。

`npm run build` 可能打印 `./styles/app.css doesn't exist at build time, it will remain unchanged to be resolved at runtime`。这是预期现象：样式是 `public/` 下的静态资源，构建后 `dist/styles/` 应包含 `app.css` 与全部分文件，与源文件一致；`dist/art/` 与 `dist/_headers` 也应在位。不必为消除这行提示而把它改成 Vite 模块导入。

运行时验证（用临时 env，端口 9102，避开线上 9002）：

```bash
cp "$REPO/.env.local" .env.local
PORT=9102 node --import tsx server.ts > /tmp/tangyou_uistan_candidate.log 2>&1 &
CAND_PID=$!
sleep 5
curl -sS -m 5 http://127.0.0.1:9102/api/health; echo
curl -sS -m 5 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9102/styles/app.css
kill "$CAND_PID" 2>/dev/null || true
wait "$CAND_PID" 2>/dev/null || true
rm -f .env.local
```

预期：lint 与 build 通过；health 返回 `ok:true`、`configured:true`；`/styles/app.css` 返回 HTTP 200。

若本机有 Chrome，且候选服务仍在 9102 监听，可再跑可选验证门（默认会访问 9002，因此需要改指向）：

```bash
VERIFY_BASE_URL=http://127.0.0.1:9102/ npm run verify -- --out verify-results/candidate
```

verify 只守非 UI 的核心业务，不锁界面。候选服务不可达时它会直接报错；只想快速确认业务层、不起服务时，可用 `npm run verify -- --no-browser`（约 9 s，但不覆盖界面到业务的接线）。产物目录 `verify-results/` 已被 `.gitignore` 忽略；提交进仓库的金样在 `scripts/verify/fixtures/golden/`（node 层四份：逻辑、锁定文案、选项值、领域层；浏览器冒烟三份：请求体、消息形态、冒烟结果）。验证门把时钟冻结在香港时间 `2026-11-26 09:30`，结果可重复；判读时以「OK: contract goldens match.」与「verify OK」为硬门。AI Studio 导出的 UI 若丢了 `data-verify` 钩子，冒烟会报「timed out waiting for [data-verify=…]」，按 `scripts/verify/README.md` 的钩子表补回即可（钩子只是属性，不改行为）。需要看 DOM / 截图差异时加 `--ui --compare <目录>`，属参考项。该步骤不是每次导入的必做项。

若 `node --import tsx` 不可用，可以改用 `PORT=9102 npm run dev`。若 9102 已被占用，可以用 `lsof -iTCP:9102 -sTCP:LISTEN` 查看。

### 5.13 干净 clone 测试

干净 clone 测试模拟“另一台机器从零重建”。可以把它理解成：把菜谱交给一个从没来过你家的人，让他在空厨房里只按菜谱做一遍。若他能做出来，说明菜谱是完整的；若失败，说明有文件或步骤没有被写进仓库。

它不是每次都必须执行，而是一道按风险分级的质量门。

| 变更类型 | 候选区验证 | 干净 clone 测试 |
| --- | --- | --- |
| 纯文档、文案、注释 | 可选 lint | 跳过 |
| 普通源码改动 | `npm ci` + lint + build；有条件时再加 `npm run verify -- --skip-build`（约 35 s；无服务时 `--no-browser`） | 可选，或每周/每月一次 |
| 依赖、lockfile、构建配置、目录结构变化 | `npm ci` + lint + build；有条件时再加 `npm run verify` | 建议必做 |
| 大范围重构、工具导出可疑、基线漂移 | `npm ci` + lint + build；有条件时再加 `npm run verify` | 建议必做 |

执行方式：

```bash
rm -rf "$CLEAN_CLONE"
git clone -b "$BRANCH" "$REPO" "$CLEAN_CLONE"
cd "$CLEAN_CLONE"
npm ci --prefer-offline --no-audit --no-fund
npm run lint
npm run build

rm -rf "$CLEAN_CLONE"
```

它验证的是提交后的仓库是否自足：不依赖候选 worktree 的本地残留，也不依赖你本机的 `.env.local`、`node_modules` 或工具生成物。若测试失败，先修复或丢弃候选，不进入合并。

### 5.14 squash 合并与人工推送

```bash
cd "$REPO"
MAIN_BRANCH="$(git branch --show-current)"

git diff --stat "$MAIN_BRANCH".."$BRANCH"
git diff "$MAIN_BRANCH".."$BRANCH" | less
```

确认 diff 后，先移除候选 worktree，避免分支被占用：

```bash
rm -rf "$CAND_WT/node_modules" "$CAND_WT/dist" "$CAND_WT/.vite" "$CAND_WT/verify-results"
git worktree remove "$CAND_WT" || git worktree remove --force "$CAND_WT"
```

squash 合并把候选分支的多个提交压成主分支上的一个提交，使一次迭代在主分支上对应一个提交，整批回退更容易；细节留在渠道归档。

```bash
git merge --squash "$BRANCH"
git commit -m "import(<渠道名>): <一句话描述本次迭代>"

git show --stat --oneline HEAD > "$CHANNEL_DIR/change_summary.txt"
git diff --stat "$BASE_COMMIT"..HEAD >> "$CHANNEL_DIR/change_summary.txt"
```

若主分支在候选创建后已有新提交，squash 合并可能出现冲突；解决冲突后重新 lint / build，再完成提交。

```bash
git worktree remove "$BASE_WT"
git branch -D "$BRANCH"

git push origin "$MAIN_BRANCH"
```

远端名以实际仓库为准；推送保持人工，不依赖 AI 工具的自动 push。若推送被拒，按团队流程先 `git pull --rebase`，不做强制推送。

## 6. 回滚与记录

### 6.1 回滚路径

| 阶段 | 回滚方式 |
| --- | --- |
| 候选区尚未提交 | 删除候选 worktree 与分支即可 |
| 候选区已提交、尚未合并 | `git branch -D "$BRANCH"`，删除 worktree |
| 已 squash 合并、尚未推送 | 确认 import commit 后，`git reset --hard <import-commit>~1` |
| 已推送 | `git revert <import-commit>` |

### 6.2 导入记录

渠道目录中的 `base_commit.txt`、`import_manifest.txt`、`export_manifest.txt`、`change_summary.txt` 构成一次导入的记录。它们描述的是本次导入的来源、范围与结果，不是历史叙事。

`import_manifest.txt` 可以在合并完成后写入：

### 8.2 命令速查

| 目的 | 命令 |
| --- | --- |
| 记录 base | `git rev-parse HEAD > "$CHANNEL_DIR/base_commit.txt"` |
| 干净快照 | `git archive --format=zip --output="$CHANNEL_DIR/base_snapshot.zip" HEAD` |
| 建立 base worktree | `git worktree add --detach "$BASE_WT" "$BASE_COMMIT"` |
| 建立候选 worktree | `git worktree add -b "$BRANCH" "$CAND_WT" HEAD` |
| 预览变化 | `rsync -avn --delete --itemize-changes --exclude-from="$STAGE/exclude.txt" "$EXPORT/" "$BASE_WT/"` |
| 叠加到候选 | `rsync -av --itemize-changes --exclude-from="$STAGE/exclude.txt" "$EXPORT/" "$CAND_WT/"` |
| 未知文件 | `git -C "$CAND_WT" ls-files --others --exclude-standard` |
| 候选区验证 | `npm ci --prefer-offline --no-audit --no-fund && npm run lint && npm run build`（确认 `dist/styles/` 含 `app.css` 与全部分文件，`dist/art/` 与 `dist/_headers` 在位；可选 `npm run verify`） |
| 干净 clone 测试 | `git clone -b "$BRANCH" "$REPO" "$CLEAN_CLONE"` |
| 移除候选 worktree | `git worktree remove "$CAND_WT"` |
| squash 合并 | `git merge --squash "$BRANCH"` |
| 人工推送 | `git push origin "$MAIN_BRANCH"` |

### 8.3 术语

- **base**：把代码交给 AI 工具时的仓库状态，通常以 commit 表示。
- **导出物**：AI 工具返回的 zip 或目录树，是候选变更集，不是仓库替代品。
- **候选 worktree**：用 `git worktree` 创建的独立工作区，用于叠加、评审与验证导出物。
- **受保护基线**：定义项目可维护性与发布口径的文件，工具可以提出修改，但需要人显式决定。
- **干净 clone 测试**：从候选分支重新 clone 到临时目录，验证提交后的仓库能否从零安装与构建。
- **渠道归档**：按来源与时间保存导出物、base、工具产物与未知文件的仓库外目录。
- **squash 合并**：把候选分支的多个提交压成主分支上的一个提交，使一次迭代对应一个提交。
