### 2.1 会话依赖问题定位

通过时间线与系统日志，逐步排除了内存、磁盘、原生崩溃与 logind 强杀：

- `session 8999` 于 02:25:01 建立，服务于 02:25:41 写入 pid、02:25:44 启动成功；
- 02:28:39 `Session 8999 logged out`，同一秒 `session-8999.scope: Deactivated successfully`，
  进程消失时间与 SSH 会话结束时间精确重合；
- `KillUserProcesses` 为默认 `no`，`systemd-oomd` 为 `inactive`，内核与 journalctl 中没有
  OOM、segfault 或 coredump；
- 磁盘与 inode 充足；
- `session-9000.scope` 在会话结束后处于 `active (abandoned)`，其中由 `setsid` 启动的
  进程仍存活，说明 logind 不会主动杀死 scope 内进程；
- `setsid` 对照实验：退出终端、合上电脑 6 分钟后重连，进程仍在，`/api/health` 正常。

由此形成的认知是：

- 进程死亡不是应用自身报错，而是 SSH 会话结束时的挂断信号作用于旧会话的进程树；
- `nohup` 的保护范围通常只覆盖直接进程；`npm → sh → tsx → node` 这种多层工具链中，
  任一环安装信号处理器或重新 exec，都可能打断忽略链；
- `setsid` 可以让进程脱离控制终端与新会话，避开终端挂断信号，但它不提供重启策略、
  开机自启、日志归集与退出码观测；
- 线上长期运行更适合交给 systemd：cgroup 隔离、生命周期管理、日志与开机集成由
  systemd 统一承接。

### 2.2 systemd 托管迁移

在确认根因后，线上服务从 `nohup` 迁移到 systemd：

- 写入 `/etc/systemd/system/tangyou_uistan.service`；
- 首次启动失败，`status=216/GROUP`：unit 中写了 `Group=webser`，但系统中不存在名为
  `webser` 的组；`id webser` 显示主组为 `webgp`；
- 去掉 `Group=`，让 systemd 使用 passwd 中的主组，服务启动成功；
- `systemctl enable --now tangyou_uistan` 后，服务处于 `active (running)`，
  `CGroup` 位于 `/system.slice/tangyou_uistan.service`；
- 断开 SSH、等待、重连后，`Main PID` 保持不变，`/api/health` 仍返回
  `ok:true`、`configured:true`。

本次迁移确认的 unit 形态为：

```ini
[Unit]
Description=tangyou_uistan (npm run dev)
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=0

[Service]
Type=simple
User=webser
WorkingDirectory=/da04/webser/sour/pro/tangyou_uistan_0
ExecStart=/usr/bin/npm run dev
Restart=always
RestartSec=3
TimeoutStopSec=10
StandardOutput=append:/da04/webser/logs/pro/tangyou_uistan_0.log
StandardError=append:/da04/webser/logs/pro/tangyou_uistan_0.log

[Install]
WantedBy=multi-user.target
```

由此形成的认知是：

- systemd 的 cgroup 归属决定了服务是否会随登录会话消失；`system.slice` 与
  `session-*.scope` 是两种不同的生命周期；
- `216/GROUP` 是身份面失配，常见原因是 `Group=` 指向不存在的组；省略 `Group=`、
  让主组由 passwd 提供，是一种更稳的默认；
- `StartLimitIntervalSec=0` 与 `Restart=always` 让服务在异常退出后持续重试；
- 日志追加到文件后，需要另行关注轮转；systemd 的 `journalctl` 主要记录 unit 生命周期。

### 2.4 仓库纯净性与 AI 迭代成果回灌

本阶段同时处理了“AI 工具迭代成果如何进入仓库”的治理问题。

原始脚本的做法是：

- 解压 AI 工具导出物到临时目录；
- 将 `.git`、`.idea`、`node_modules`、`.env.example`、`.env.server.local`、
  `.gitignore`、`.nvmrc` 移出仓库；
- 使用 `rsync -avm` 将导出物叠加到仓库，不带 `--delete`；
- 再将移出的文件移回；
- 手动还原误删文件、删除应删文件、清理工具特有文件；
- 人工提交并推送。

其本意是：仓库只保留与项目本身相关的文件，不包含各 AI 编程工具带来的额外产物；
仓库应可被人手工维护与迭代，也可被任意 AI 工具临时拿去迭代；迭代完成后，通过一套
可重复的流程把成果干净地回灌到仓库。

本阶段将该本意整理为：

- 七颗方向性北极星：走向语义自足、走向人的可接手性、走向工具可替换性、走向可复现性、
  走向可逆性、走向人的最终主权、走向可持续的低摩擦；
- 一张张力空间：纯净/开放 × 人的判断/机器自动化；
- 一套文件分类：本地专属、受保护基线、工具产物、未知文件；
- 一条回灌流程：记录 base → 干净出站快照 → 解压归档 → base worktree → 候选 worktree
  → 三方对比 → 工具产物清扫 → 未知文件隔离 → 受保护基线评审 → 删除候选评审 →
  候选区验证 → 提交候选 → 干净 clone 测试 → squash 合并 → 人工推送；
- 一个渠道归档根目录：`/Users/davie/Desktop/scrapt/tangyou_uistan/iteration_channels/`，
  每个来源一个渠道目录，每次导入一个时间戳目录，完整保留导出物、base 与清单；
- 一个关键取舍：主分支一次迭代对应一个 squash 提交，候选分支细节留在渠道归档。

================================================================================
三、核心取舍与设计依据
================================================================================

1. 为何用 systemd 替代 nohup/setsid
   - `nohup` 对多层工具链的保护不可靠，且不提供重启、开机自启、日志归集与退出码观测；
   - `setsid` 能解决会话脱离，但仍缺少生命周期管理；
   - systemd 将服务放入独立 cgroup，提供重启、开机自启、日志与验收所需的观测面。

2. 为何省略 `Group=`
   - 首次 systemd 启动失败为 `216/GROUP`，原因是 `Group=webser` 指向不存在的组；
   - `User=webser` 时，systemd 会使用 passwd 中的主组 `webgp`；
   - 省略 `Group=` 降低了对组名解析的依赖。

3. 为何项目实例文档独立存在
   - 项目实例文档需要直接指导 `tangyou_uistan` 的搭建、复现与运维；
   - 通用规范适合作为“从零设计”的方法论文档，不应成为实例文档的前置依赖；
   - 最终知识库只保留项目实例文档，避免同一事项在两份文档中漂移。

4. 为何手动指南合并为一份
   - macOS 本地与 Linux 线上共享运行时形态、`.env.local`、health、冒烟与迭代判断；
   - 环境差异集中在“从零搭建”与“命令前缀、路径、权限”；
   - 一份文档减少重复维护，符合“走向可持续的低摩擦”。

5. 为何统一 Node 24
   - 仓库 `.nvmrc` 为 24；
   - Node 24 兼容 Node 22，项目已有运行基础；
   - 本地与线上统一版本，减少环境漂移。

6. 为何手动指南只做 dev 模式
   - 本阶段目标是先建立可被人执行的手动基线，快速验证；
   - 生产构建与生产托管属于另一条链路，暂不混入手动教程；
   - systemd 实例当前也以 `npm run dev` 为运行命令，保持一致。

7. 为何线上手动模式只用前台
   - 首次线上验证的目标是快速确认服务、环境变量与健康端点；
   - tmux/nohup 会引入额外进程管理复杂度；
   - 验证通过后直接交给 systemd，避免形成第二套临时托管习惯。

8. 为何主分支采用 squash 合并
   - 一次 AI 迭代渠道的改动，最终在主分支形成一个提交；
   - 整批回退容易，主分支历史清晰；
   - 候选分支的细节与导入来源留在渠道归档中。

9. 为何保留渠道归档
   - 被排除的 `.idea`、工具产物与未知文件不会丢失；
   - base、导出物与清单可用于三方对比与审计；
   - 需要时可以从归档中按原始目录树找回文件。

10. 为何用 `git worktree` + 干净快照，而不是继续移走文件
    - 出站快照只包含已跟踪文件，工具从一开始就看不到 `.git`、`node_modules`、`.idea`；
    - 入站叠加发生在候选 worktree，活仓库不参与中间状态；
    - 保护从“记得把哪些文件移走”变成“结构上不进入叠加路径”。

11. 为何删除旧重启指南
    - 其运行态内容已由手动指南承接；
    - 其 systemd 内容已由 systemd 实例承接；
    - 其 AI Studio 导出物与锁文件内容已由仓库回灌实践承接；
    - 保留旧指南会造成同一事项多处分叉。

12. 为何索引只做必要修改
    - 目录拓扑变化需要校准入口地图；
    - 三颗北极星、三份只读基石、历史归档机制与文笔心法不属于本次变更面；
    - 仅替换旧指南引用、增补新文档描述、更新阅读路径、信息流与速览表，
      并对既有失真文件名做精准校准。
