### 2.2 可行性分析

分析在仓库外的临时目录中进行，没有改仓库，也没有在 Cloudflare 上创建资源。本地用 wrangler 把现有 Express 与 `/api/gemini/*` 原样挂进 Worker 入口后，健康检查、真实 Gemini 对话（粤语回复正常）、约 12 MB 的请求体、首页、样式与 SPA 回落均可用。`@google/genai` 在 Workers 里走 web 版，不依赖文件系统。

当时已经看清的硬约束是：Gemini API 不对香港地区开放，而香港用户的请求默认会在 Cloudflare 的香港机房执行。本地出口不在香港，地区限制在分析阶段无法实测。其他需要预先说明的点包括：免费套餐每次请求只有 10 ms CPU，照片和录音请求很可能不够用；若把整个 `tangyou-app` 域名切到 Worker，同一主机名下的上报路径会受影响，必须单独安排；503 后“60 秒只用快速模型”的冷却在 Node 上是每进程一份。

推荐方案是 Workers + 静态资源，Express 经兼容层原样运行：`dist/` 由 Static Assets 托管，`/api/*` 交给 Worker。为让 Worker 与 `server.ts` 行为一致，需要把共用部分抽成 `createApp()`，这会小改受保护的 `server.ts`。Pages Functions、只把静态页放 Cloudflare、或用另一套框架重写 API，都不作为首选。

### 2.3 稳定优先下的形态选择与分支实现

主人选择开通 Workers 付费套餐，并以稳定优先处理 Gemini 地区限制：不采用“指定东京运行”这类不一定每次生效的调度提示，而把调用 Gemini 的路径放进首次建立于美西（`locationHint: "wnam"`）的 Durable Object。代价是每次 `/api/*` 大约多 150 ms 内部往返。

实现落在 `feat/cloudflare-workers` 上，相对 `main @ e49c68f` 的前三个提交时间约为 2026-11-26 15:28（香港时间）：

- `94056d1` 把 25mb JSON 上限、`/api` 的 `Cache-Control: no-store`、以及 health 与 gemini 路由的注册抽到 `server/app.ts` 的 `createApp()`。`server.ts` 仍先加载本地环境再创建应用，随后的 Vite / `dist/` 处理、端口与启动日志与原先一致。
- `4f26455` 新增 `cloudflare/worker.ts`、`cloudflare/cloudflare-node.d.ts` 与 `wrangler.jsonc`。Worker 按路径分流：静态资源走 `dist/`；`/api/*` 交给名为 `gemini-egress-v1` 的单例 Durable Object，DO 内用同一份 `createApp()` 处理；`/chtatain-datacent/*` 按 `UPLOAD_ORIGIN` 反向代理到旧源站。`package.json` 只增加 `cf:dev` 与 `cf:deploy`（`vite build && npx --yes wrangler@4.168.0 dev|deploy`），既有脚本与依赖不变，锁文件不变。wrangler 故意不写入 devDependency，以免其约 100 MB 的二进制拖慢每次 `npm ci` 与 AI Studio 安装。`.gitignore` 增加 `.dev.vars*` 与 `.wrangler`。这一提交里，正式域名的 `routes` 仍保持注释，以免尚未批准就把流量切走。
- `afc7098` 新增《线上无服务器部署实例（Cloudflare Workers）.txt》，并同步 00 索引、手动搭建指南、仓库纯净性文档与 README。北极星、核心业务明细、须知与 systemd 文档未改。

Durable Object 的设计取舍在后来的渠道文档中写清，这里只记录当时已经成立的几点：由 DO 承载整个 Express 应用而不是只转发一次 fetch，是为了让路由、提示词、回退与错误文案与 Node 端零分叉；冷却状态因此从“每进程一份”变成“单例 DO 全局一份”，DO 被回收后重置，等价于进程重启；Route 模式被选为正式域名方案，是因为可以保留指向旧伺服器的橙云 A 记录，使同 zone 子请求直达 DNS 源站，从而让 `UPLOAD_ORIGIN` 仍写正式主机名本身，删除 Route 即可回滚。这一同 zone 行为当时无法在本地模拟，被明确列为必须在正式切换后实测的项。

### 2.4 独立差分复核与两处仅影响 Workers 的修补

主人要求以阅读 `main @ e49c68f` 与当时分支（至 `afc7098`）之 diff 的方式，独立判断是否出现破坏性改动。复核结论是：没有破坏性改动。前端、提示词、业务逻辑与锁文件的 diff 为空；构建出的前端包与 `main` 完全相同，Worker 代码没有混进前端；`createApp()` 抽取后，中间件顺序、请求体上限、缓存头、404 与 SPA 回落与原先一致。复核用 `main` 与新分支各起服务，在 dev 与生产两种模式下对照多类请求，状态码与响应内容一致。`package.json` 只新增两个脚本。提交记录中未发现密钥。

复核列出的建议项只影响 Workers 形态：Durable Object 不可达时，若没有捕获，用户可能看到平台 HTML 500，而不是应用既有的中文错误 JSON；上报代理若原样转发全部请求头，会把 `Host`、`cf-*`、`X-Forwarded-For` 等带给旧源站，旧服务看到的客户端 IP 也会变化。另外，复核初稿曾认为生产模式下 `GET /api` 在 Node 与 Worker 上不一致，后来用 9002 与 `npm start` 实测，两边都是 JSON 404，这一条被更正为无差异。

主人授权修补后，分支上追加：

- `276f243`（约 15:43）：`cloudflare/worker.ts` 在转发到 DO 失败时返回 503 `{"error":"AI 服務暫時無法處理請求，請稍後再試。"}` 且带 `Cache-Control: no-store`（文案沿用既有错误默认值，不重试，以免请求体已被读取）；上报代理改为在新的请求头集合中只保留业务头，去掉逐跳头与 Cloudflare / 代理链头，并把 `X-Forwarded-For` 设为 `CF-Connecting-IP` 的值。

这两处随后在本地 `wrangler dev` 下复测：真实对话仍返回 200；用临时配置模拟 DO 抛错时得到上述 503 JSON；上报桩服务收到业务头与由 `CF-Connecting-IP` 写入的 `X-Forwarded-For`，未收到伪造的链路头（运行时自动附加的 `CF-Worker` 除外）。Node 服务代码、前端、提示词、依赖与锁文件在复核之后仍然没有改动。

三、方案权衡与取舍依据
================================================================================

- 运行时形态选择 Workers + Static Assets + 原样 Express，而不是 Pages Functions 或另一套 API 框架，是为了让 `/api/gemini/*` 的实现只有一份，避免两套提示词与错误文案逐渐分叉。
- 抽出 `createApp()` 而不是在 Worker 里复制一份路由，是为了让 Node 入口与 Workers 入口共享同一份中间件顺序和契约；`server.ts` 的启停语义保持不变，AI Studio 流程继续不读取 wrangler 配置。
- 把 Gemini 出站放进美西 Durable Object，而不是依赖 `placement.region` 或另建中转伺服器，依据是主人“稳定优先”的明确选择，以及香港地区不被 Gemini 支持这一硬约束。
- 正式域名用 Route、不改 DNS，而不是 Custom Domain，依据是上报路径必须继续到达旧伺服器，并且回滚动作要能立刻把流量交回旧源站。
- wrangler 不写入依赖、只用带版本号的 `npx` 调用，依据是不拖慢 `npm ci` 与 AI Studio 安装，同时把版本钉在本阶段验证过的 `4.168.0`。
- 先 `*.workers.dev`、后挂正式域名 Route，依据是地区限制只能在香港网络上证实，以及主人要求先在测试地址试用。
- 首次上线用 `--secrets-file`（或先 `secret put` 再部署），依据是避免 Worker 在没有密钥的窗口里对外提供 `configured:false`。

本阶段结束时仍未做、需要后续单独决定的事项：

- 本分支尚未合并进 `main`，也尚未开拉取请求；
- 线上 Worker Secret 使用的仍是阶段开始前那把已存在的 Gemini 密钥。该密钥此前曾在对话中出现过，正式环境建议由资源拥有者轮换，并同步到仍在运行的旧伺服器 `.env.local` 后重启服务；本归档不记录密钥本身；

- `locationHint` 只在名为 `gemini-egress-v1` 的 Durable Object 第一次建立时生效；若将来要换出站地区，需要同时更换实例名；

七、阶段结论
================================================================================

在项目主人按节点授权的前提下，本阶段把 `tangyou_uistan` 的同一份核心业务代码，增加了一条不依托应用伺服器的线上发布渠道，并已在正式域名 `tangyou-app.alphathought.org` 上切换成功。Node 入口与 AI Studio 回灌重启流程保持可用；核心业务逻辑、文案、提示词与锁文件不在本阶段的改动范围内。独立差分复核确认：复核时点之前的改动没有破坏既有 Node 形态；复核之后仅有 Workers 侧错误处理、上报请求头过滤，以及正式域名 Route 配置三类非文档变更。
