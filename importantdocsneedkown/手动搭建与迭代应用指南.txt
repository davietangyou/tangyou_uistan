## 0. 定位与阅读路径

### 0.1 这份文档覆盖什么

本文档描述 `tangyou_uistan` 在两类白板机器上的手动搭建与迭代应用：

- **macOS 本地机器**：从零准备 Node 24、获取代码、安装依赖、配置 `.env.local`、手动启动、验证；以及新代码进入仓库后的停止、拉取、依赖更新、重启与验证。
- **Linux 线上服务器**：从零准备用户、组、目录、Node 24、代码、依赖、`.env.local`、前台手动启动、验证；以及新代码进入仓库后的停止、拉取、依赖更新、重启与验证。

两份场景共享同一套运行时形态、环境变量、健康检查与迭代判断逻辑；差异集中在“从零搭建”与“命令前缀、路径、权限”上。

### 0.2 这份文档不覆盖什么

- AI 工具导出物如何进入仓库：由另一份仓库回灌文档负责；
- 线上 systemd 长期托管：由 systemd 实例文档负责；
- 反向代理、TLS、DNS：由上层设施负责；
- 生产构建与生产托管：本文档只使用 dev 模式；
- Cloudflare Workers 无服务器部署：由《线上无服务器部署实例（Cloudflare Workers）.txt》负责。它是与本文档及《线上服务托管实例（systemd）》并列的一条线上发布渠道；持有本仓库代码的执行者可依据该文档，与资源拥有者沟通后发布到指定的 Cloudflare 账号与指定域名。它与本文档的 dev 模式共用同一套 `/api/gemini/*` 路由代码（`server/app.ts`），互不改变对方的启动方式；
- AI 辅助发布：属于另一条独立链路。

## 1. 通用运行时形态

### 1.1 单进程结构

`tangyou_uistan` 的 dev 模式由一条命令启动：

```
npm run dev
  → tsx server.ts
  → Express + Vite middleware
  → 浏览器页面与 /api/gemini/* 同源
```

浏览器访问 `http://127.0.0.1:9002/`，前端与后端 API 由同一个进程提供。Vite middleware 负责前端资源与热更新；`server.ts` 负责 `/api/gemini/*` 与 `/api/health`。这些 API 路由（含 25mb JSON 上限与 `/api` 的 `Cache-Control: no-store`）由 `server/app.ts` 的 `createApp()` 组装，`server.ts` 在其后挂载 Vite middleware 或 `dist/` 并监听 `0.0.0.0:PORT`；Cloudflare Workers 入口 `cloudflare/worker.ts` 复用同一个 `createApp()`，dev 模式不读取 `wrangler.jsonc`。

### 1.2 端口与环境变量

- 默认端口由 `.env.local` 的 `PORT=9002` 指定；
- `server.ts` 启动时经 `server/env.ts` 按以下顺序读取环境变量，且不覆盖已存在的进程环境变量：

```
进程环境变量 ＞ .env.server.local ＞ .env.local ＞ .env
```

- `.env.local` 是机器专属文件，不进入仓库；
- `.env.example` 是字段模板，进入仓库；
- 环境变量的读取实现位于 `server/env.ts`，由 `server.ts` 启动时调用。

### 1.3 dev 模式的边界

dev 模式下：

- 前端改动由 Vite 热更新；
- `server.ts`、`server/*.ts` 等后端改动不会自动重载，需要重启进程；
- 进程是前台进程，终端关闭或 `Ctrl+C` 会停止服务；
- 线上前台运行期间，SSH 会话保持连接；会话断开，进程会随之结束。

长期线上托管由 systemd 实例文档负责；本文档的线上手动模式只用于首次快速验证。

### 1.4 页面样式资源

页面皮肤与大字规则写在仓库内的 `public/styles/app.css`。`index.html` 在 Tailwind CDN 之后引入：

```html
<link rel="stylesheet" href="%BASE_URL%styles/app.css">
```

dev 模式下，Vite 把 `public/` 作为静态根目录，浏览器实际请求 `/styles/app.css`。服务起来后可用下面的命令确认该资源在位：

```bash
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9002/styles/app.css
```

预期 HTTP 200，正文与 `public/styles/app.css` 一致。若同步或解压后缺少该文件，Tailwind 工具类仍可用，但整套界面样式（设计令牌、`ds-*` / `t-*` 类、大字模式）会丢失，各页面基本失去版式。

UI 重构合并（main `c18afb1`）后，该文件约 112 KB：前 4550 字节是重构前的原规则，保持逐字节不变（`head -c 4550 public/styles/app.css | sha256sum` 应为 `b864594f30dc4a8fcc526161c3b185e40c3cfbb84e0243c824e8ed8e7e2da29e`）；其后追加的是设计系统与各视图样式，新视图以 `.ds-root` 承载、控件加 `.ds-control` 以避开旧的 `.large-font` 强制规则。对应的 React 基础组件在 `components/ui/`。新增样式只在文件末尾追加。

本文只覆盖 dev 模式。若改走 `npm run build && npm start`，构建会把该文件原样复制为 `dist/styles/app.css`，页面链接变为相对路径 `./styles/app.css`。`npm run build` 可能打印：

```
./styles/app.css doesn't exist at build time, it will remain unchanged to be resolved at runtime
```

这是预期现象：该文件是 `public/` 下的静态资源，不是 Vite 模块。不必为消除这行提示而把它改成源码里的 CSS import——那样会改写颜色与标签顺序。

## 2. 通用配置：`.env.local`

### 2.1 字段表

| 字段 | 是否必填 | 当前参考值 | 说明 |
| --- | --- | --- | --- |
| `GEMINI_API_KEY` | 必填 | 由部署方提供 | Google Gemini API Key |
| `PORT` | 可选 | `9002` | 服务监听端口 |
| `GEMINI_MODEL` | 可选 | 未设置 | 覆盖默认文本模型 |
| `GEMINI_VISION_MODEL` | 可选 | 未设置 | 覆盖识图模型；未设置时回退 `GEMINI_MODEL` |
| `GEMINI_TRANSCRIBE_MODEL` | 可选 | 未设置 | 覆盖语音转写模型 |
| `GEMINI_FAST_MODEL` | 可选 | 未设置 | 覆盖日常轻量咨询的快速模型 |
| `GEMINI_BASE_URL` | 可选 | 未设置 | 受限网络下的中转/反代 Base URL |

### 2.2 加载顺序

`server.ts` 启动时经 `server/env.ts` 的加载顺序：

```
进程环境变量 ＞ .env.server.local ＞ .env.local ＞ .env
```

已存在的进程环境变量不会被覆盖。对于手动模式，`.env.local` 已经足够；进程环境变量可以用于临时覆盖，例如：

```bash
PORT=9102 npm run dev
```

### 2.3 权限与密钥边界

- `.env.local` 不进入 Git，也不进入任何 AI 工具快照；
- 线上 `.env.local` 权限为 600，属主为 `webser:webgp`；
- 密钥不写入 unit 文件、不写入日志、不写入提交；
- 检查字段是否设置时，可以用 `sed` 隐藏值：

```bash
grep -E '^(GEMINI_API_KEY|PORT)=' .env.local | sed 's/=.*/=<set>/'
```

## 3. 通用验证：health 与冒烟

### 3.1 健康端点

```bash
curl -sS http://127.0.0.1:9002/api/health; echo
```

参考返回：

```json
{"ok":true,"configured":true,"model":"gemini-4-hydrogen","fastModel":"gemini-3.1-flash-lite","visionModel":"gemini-4-hydrogen","transcribeModel":"gemini-3.5-transcribe","customBaseUrl":false}
```

重点字段：

| 字段 | 含义 |
| --- | --- |
| `ok` | 服务进程可响应 |
| `configured` | `GEMINI_API_KEY` 是否已配置 |
| `model`、`fastModel`、`visionModel`、`transcribeModel` | 当前模型路由 |
| `customBaseUrl` | 是否启用了 `GEMINI_BASE_URL` |

样式资源也可以一并确认：

```bash
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9002/styles/app.css
```

预期 HTTP 200。

### 3.2 浏览器冒烟

本地入口：

```
http://127.0.0.1:9002/
```

线上入口（反向代理已配置时）：

```
https://tangyou-app.alphathought.org/
```

建议的冒烟项：

- 文字 AI 问答：发送一条血糖或饮食相关问题，确认回复正常返回；
- 拍照识药：在「個人檔案 → 拍照識藥」上传一张药袋/药盒照片，确认识药接口返回；
- 问题总结：在「問題紀錄 → AI 總結」触发一次总结，确认分类与建议问题正常；
- 语音输入：聚焦输入框，点击全局麦克风录音，确认转写结果填入。

若线上反向代理尚未配置，可以在服务器本机用 `curl` 验证 health；是否对外开放 9002 取决于安全组与防火墙，本文档不展开。

### 3.3 停止方式

- 本地前台：终端 `Ctrl+C`；
- 线上前台：终端 `Ctrl+C`；
- 若 `Ctrl+C` 后端口仍被占用，可以用端口检查定位进程：

本地：

```bash
lsof -iTCP:9002 -sTCP:LISTEN
```

线上：

```bash
sudo ss -ltnp | grep 9002
```

无输出表示端口已释放。若有残留进程，可以按 PID 结束。

### 3.4 可选：无损改动验证门

日常启动不必执行。做不应改变客户端可见行为的改动时，可用仓库内的验证门：

```bash
npm run verify
```

该命令对应 `package.json` 的 `verify` 脚本（`node scripts/verify/run.mjs`）。完整的 DOM 与交互快照需要本机 dev 已在 9002 监听，并有 Chrome。产物写在 git 忽略的 `verify-results/`；提交进仓库的金样在 `scripts/verify/fixtures/golden/`。与某次基线对照时，可以加上 `--out` 与 `--compare`，例如：

```bash
npm run verify -- --out verify-results/phase-N --compare verify-results/baseline
```

验证门会把浏览器时钟冻结在香港时间 `2026-11-26 09:30`，结果可重复。输出「OK: contract goldens match.」且 status 全 0 即契约无损；`--compare` 的 DOM / 截图差异在界面改动时属预期，需逐项确认来由。

不要把 `verify-results/` 提交进仓库，也不必拷到线上托管目录。更细的说明见 `scripts/verify/README.md`。

## 4. 通用迭代应用流程

### 4.1 步骤

一次新迭代进入仓库主分支后，应用流程可以按以下顺序进行：

1. 停止当前手动服务；
2. 记录当前 commit；
3. 确认工作区状态；
4. 拉取主分支最新代码；
5. 查看变更文件；
6. 判断是否需要更新依赖；
7. 判断是否需要更新 `.env.local`；
8. 重新启动；
9. 健康检查与浏览器冒烟；
10. 必要时回退。

### 4.2 依赖与环境变化判断

| 变更文件 | 动作 |
| --- | --- |
| `package.json` | 执行 `npm ci`，然后重启 |
| `package-lock.json` | 执行 `npm ci`，然后重启 |
| `.env.example` | 对比差异，必要时更新 `.env.local` |
| `vite.config.ts` | 重启 |
| `server.ts` / `server/**` | 重启 |
| `public/styles/app.css` 或 `index.html` 中的样式链接 | 确认文件仍在；刷新或重启后检查大字开/关外观 |
| `scripts/verify/**` | 通常无需重启；金样变更时再按需跑 `npm run verify` |
| `wrangler.jsonc` / `cloudflare/**` | dev 模式无需重启；只影响 Cloudflare Workers 部署形态 |
| 前端源码 | 手动流程下重启（Vite 热更新只在运行中生效） |
| 仅文档 | 通常无需重启 |

判断依赖是否变化：

```bash
git diff --name-only "$OLD_HEAD"..HEAD | grep -E 'package(-lock)?\.json'
```

判断 `.env.example` 是否变化：

```bash
git diff "$OLD_HEAD"..HEAD -- .env.example
```

### 4.3 本地命令序列

```bash
# 1. 停止：在前台终端按 Ctrl+C

# 2. 进入项目目录
cd /Users/davie/Desktop/EffLearn/tangyou_uistan

# 3. 若新开终端，先确认 Node 版本
node -v

# 4. 记录旧 commit
OLD_HEAD="$(git rev-parse HEAD)"

# 5. 确认工作区状态
git status --porcelain

# 6. 拉取
git pull --ff-only

# 7. 查看变更文件
git diff --name-only "$OLD_HEAD"..HEAD

# 8. 若 package.json / package-lock.json 变化
npm ci --prefer-offline --no-audit --no-fund

# 9. 若 .env.example 变化
git diff "$OLD_HEAD"..HEAD -- .env.example

# 10. 重新启动
npm run dev
```

若 `git status --porcelain` 有输出，可以先提交、stash 或确认这些本地改动是否需要在拉取前处理；`git pull --ff-only` 在分叉时会失败，此时需要先解决分支状态。

### 4.4 线上命令序列

```bash
# 1. 停止：在前台终端按 Ctrl+C

# 2. 进入项目目录
cd /da04/webser/sour/pro/tangyou_uistan_0

# 3. 确认运行用户看到的 Node 版本
sudo -H -u webser node -v

# 4. 记录旧 commit
OLD_HEAD="$(sudo -H -u webser git rev-parse HEAD)"

# 5. 确认工作区状态
sudo -H -u webser git status --porcelain

# 6. 拉取
sudo -H -u webser git pull --ff-only

# 7. 查看变更文件
sudo -H -u webser git diff --name-only "$OLD_HEAD"..HEAD

# 8. 若 package.json / package-lock.json 变化
sudo -H -u webser npm ci --prefer-offline --no-audit --no-fund

# 9. 若 .env.example 变化
sudo -H -u webser git diff "$OLD_HEAD"..HEAD -- .env.example

# 10. 重新启动
sudo -H -u webser npm run dev
```

### 4.5 回退

本地：

```bash
cd /Users/davie/Desktop/EffLearn/tangyou_uistan
git reset --hard "$OLD_HEAD"
npm ci --prefer-offline --no-audit --no-fund
npm run dev
```

线上：

```bash
cd /da04/webser/sour/pro/tangyou_uistan_0
sudo -H -u webser git reset --hard "$OLD_HEAD"
sudo -H -u webser npm ci --prefer-offline --no-audit --no-fund
sudo -H -u webser npm run dev
```

回退前先停止当前服务，并确认工作区没有需要保留的本地改动；`git reset --hard` 会丢弃未提交内容。

## 6. 线上 Linux 从零搭建

### 6.1 基础工具

以 Debian 12 / Ubuntu 22.04+ 为参考：

```bash
sudo apt-get update
sudo apt-get install -y git curl rsync nano iproute2
```

### 6.2 数据盘检查

本文档以 `/da04` 作为数据盘挂载点：

```bash
findmnt /da04
df -h /da04
```

若 `/da04` 尚未挂载，先完成挂载；本文档后续路径都以 `/da04` 为根。若新机器没有独立数据盘，也可以在根盘创建 `/da04` 目录，但需要确认磁盘空间。

管理员组按发行版处理：

## 8. 常见问题

### 8.1 本地

| 现象 | 可能原因 | 检查 |
| --- | --- | --- |
| `nvm: command not found` | shell 未加载 nvm | 新开终端，或 source `~/.zshrc` / `~/.bash_profile` |
| `EADDRINUSE` | 9002 被占用 | `lsof -iTCP:9002 -sTCP:LISTEN`，结束对应进程 |
| `configured:false` | `.env.local` 缺失或密钥为空 | 检查文件路径与 `GEMINI_API_KEY` |
| 模型 404 | 当前 Key 或网关不支持默认模型 | 在 `.env.local` 设置可用的 `GEMINI_MODEL` 等 |
| 网络超时 | 无法直连 Gemini 域名 | 设置 `GEMINI_BASE_URL` |
| `npm ci` 失败 | 依赖安装异常（lockfile 现已对齐，正常应可 npm ci） | 先重试 `npm ci`；仍失败再改用 `npm install` 并评审 lockfile |
| 浏览器 404 | 访问端口与 `PORT` 不一致 | 确认 `.env.local` 的 `PORT` 与 URL |
| 页面字体或卡片样式异常，但 Tailwind 仍在 | 缺少 `public/styles/app.css`，或 `index.html` 未引入该样式表 | `ls public/styles/app.css`；`curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9002/styles/app.css` 应为 200 |
| `node -v` 不是 v24 | 新终端未执行 `nvm use` | 进入项目目录执行 `nvm use`，或设置 `nvm alias default 24` |

### 8.2 线上

| 现象 | 可能原因 | 检查 |
| --- | --- | --- |
| 权限拒绝 | 项目、日志或 `.env.local` 属主不对 | `ls -ld`、`chown -R webser:webgp` |
| `configured:false` | `.env.local` 缺失或密钥为空 | 检查文件路径与 `GEMINI_API_KEY` |
| `EADDRINUSE` | 旧手动实例未退出 | `sudo ss -ltnp \| grep 9002` |
| `node: command not found` | `sudo -H -u webser` 的 PATH 或 Node 安装问题 | `sudo -H -u webser which node`、`node -v` |
| `/da04` 不存在 | 数据盘未挂载 | `findmnt /da04` |
| 反向代理 502/404 | 上游 9002 未监听或代理配置不对 | 先 `curl 127.0.0.1:9002/api/health` |
| 页面字体或卡片样式异常，但 Tailwind 仍在 | 缺少 `public/styles/app.css`，或 `index.html` 未引入该样式表 | `ls public/styles/app.css`；`curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9002/styles/app.css` 应为 200 |
| SSH 断开后服务消失 | 前台进程随会话结束 | 手动阶段用前台验证；长期用 systemd |
| 模型 404 / 网络超时 | 同本地 | 检查模型覆盖与 `GEMINI_BASE_URL` |
