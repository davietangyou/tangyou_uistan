# 糖友導航 DiaGuide HK — 核心业务逻辑文档集

---

## 这个系统是什么

糖友導航是一个面向**香港糖尿病长者**（"老友記"）的AI辅助衛教与决策支持工具。

它不做诊断、不改药、不出处方。它是**医疗决策的协作者**——帮助长者理解自身的血糖数据、在面临治疗选择时澄清自己的价值观、准备好与医生进行有质量的共同决策对话。

---

## 面向的用户群体

- 香港糖尿病长者（以2型糖尿病为主，兼顾其他类型）
- 使用广东话（粤语）作为日常语言
- 可能存在不同程度的健康素养(health literacy)限制——部分用户可能不理解医学术语、不熟悉数字化工具
- 可能独居无照护者，也可能有家人协助

系统的所有设计决策以这个用户群体为出发点——语言使用地道广东话口语而非标准书面语、默认开启大字显示模式、信息呈现追求低认知负荷。

---

## 核心价值承诺——三条腿

系统的全部存在意义，是帮助长者获得三样东西：

**1. 充分的信息。** 通过循证的临床知识（ADA国际标准、香港官方指引）和个人化的数据分析，让长者理解自己的血糖状况、治疗选项的利弊。

**2. 清晰的自我认知。** 通过结构化的价值澄清流程，帮助长者发现和表达自己在面临治疗选择时最在意什么——怕痛？担心依赖？重视便利性？这些价值偏好只有长者自己知道，系统帮助他们将模糊的感受转化为清晰的表达。

**3. 有效的沟通能力。** 通过问诊备忘、AI总结、问诊清单、就诊日期提醒，让长者带着整理好的问题走进诊室——在有限的就诊时间内，能与医生进行有质量的共同决策对话。

三条腿缺一不可。只有信息没有自我认知，长者知道很多但不知道自己要什么；只有自我认知没有信息，长者知道自己要什么但不知道选项的利弊；有了信息和自我认知但没有沟通能力，好不容易建立的知情度在5分钟的门诊对话中无法被有效传递。

---

## 设计背后的方法论框架

系统的设计根植于以下经过同行评审和实证验证的临床方法论：

**共同决策（Shared Decision-Making, SDM）**——在偏好敏感的医疗决策中，没有客观上"最好"的选择，只有对特定患者而言"最合适"的选择。"最合适"取决于患者的价值观。医生持有临床知识，患者持有个人价值——两者结合才能做出好的决策。

**患者决策辅助（Patient Decision Aid, PDA）**——基于IPDAS国际标准的工具设计：呈现平衡的信息、帮助患者澄清价值、不引导患者偏向特定选项、披露信息来源。

**Ottawa Decision Support Framework (ODSF)**——决策需求评估框架：评估患者面临的是信息需求还是决策需求，据此选择教育路径或SDM路径。

**Elwyn三阶段模型（Three-Talk Model）**——Team Talk（建立协作关系）→ Option Talk（呈现选项利弊）→ Decision Talk（基于价值做决策）。系统的终极指向是**准备患者进入与真实医生的Decision Talk**——Layer 4的问诊议题、问诊备忘、问诊清单，都是为了这最后一步。

**动机式访谈（Motivational Interviewing, MI）**——面对患者的饮食习惯时先同理再引导（"我知道你中意食榴槤，但可以试下控制份量……"），禁止责备式语言。

**Health Literacy Universal Precautions**——不是"如果用户素养低就简化"，而是**默认就采用最易理解的方式**——所有用户都受益于更清晰的表达。

**慢性病照护模型（Chronic Care Model, CCM）**——系统整体定位为Self-Management Support Tool，帮助患者建立日常自我管理的能力和信心。

---

## 核心功能模块与相互关系

系统由以下核心功能模块构成：

**用户健康档案体系** — 全局信息中枢。存储用户的全部健康信息，是所有个人化服务的基座。几乎所有其他模块都读取它或写回它。

**AI决策支持引擎** — 系统的灵魂。基于SDM/PDA方法论，通过安全检测→场景分类→价值澄清→循证推理→个人化输出的推理管线，为长者提供决策支持。

**血糖与健康指标记录体系** — 帮助长者记录和理解血糖、症状、糖化血红素数据。

**用药提醒体系** — 帮助长者按时服药，防止漏服。

**问诊备忘与就诊准备体系** — 从AI对话到诊室的"最后一公里"——积累问题、AI总结、精选清单、日期提醒。

**系统基础设施** — 引导流程、数据持久化、语音输入、药物识别等支撑系统运作的基础能力。

**模块间的核心数据流：**

```
用户健康档案 ←→ AI决策支持引擎（双向：注入Profile + AI写回累积认知）
血糖/症状记录 → AI决策支持引擎（单向：最近10条注入AI对话上下文）
AI决策支持引擎 → 问诊备忘（单向：用户从AI回复中保存有价值的要点和问题）
用户健康档案 → 用药提醒（单向：从药物清单匯入提醒）
药物图片识别 → 用户健康档案（单向：识别结果写入药物清单）
问诊备忘 → 首页展示（单向：清单和日期提醒同步显示）
```

**模块依赖关系（影响实现顺序）：**
- 用户健康档案是一切的基座——AI引擎、用药提醒、个人化问候都依赖它
- 血糖记录需要在AI对话之前存在——因为会被注入AI上下文
- AI引擎依赖安全门、场景分类、知识库、偏好维度体系——这些是它的组成部分
- 问诊备忘依赖AI对话的输出——保存的来源是AI回复中的要点和问题

# 用户健康档案体系

---

## 定位

用户健康档案是整个系统的**全局信息中枢**。它存储每位用户的完整健康信息——从基本人口学资料到糖尿病诊断、用药、共病、生活方式、风险标志、AI从对话中累积的认知。

几乎所有其他功能模块都与档案存在读取或写回关系：

- **AI决策支持引擎**：每次对话都将档案格式化为文本注入AI的推理上下文（读取），对话后AI自动提取新信息写回档案（写回）
- **用药提醒**：从档案的药物清单匯入提醒项目（读取）
- **安全防护门**：根据档案中的临床风险标志动态调整安全检测灵敏度（读取）
- **BMI评估**：根据档案中的年龄字段决定采用长者标准还是成人标准（读取）
- **引导流程**：首次设置时写入基础信息（写回）
- **药物图片识别**：识别结果写入药物清单（写回）
- **个人设定**：用户随时手动编辑（写回）

这种"读-写"双向关系构成了一个**累积认知循环**：用户提供初始信息 → AI基于信息提供个人化服务 → AI从对话中提取新信息写回 → 下次对话基于更丰富的信息提供更精准的服务。这个循环映射了临床实践中的**纵向患者理解（Longitudinal Patient Understanding）**——好的家庭医生在每次接触中逐步积累对患者的立体理解。

档案的完整数据通过本地持久化保存，确保同设备下次打开时所有信息完整可见。存储键值为 `dia_profile`，每次档案变更后自动保存。

档案加载时包含向后兼容的数据迁移逻辑——旧格式的单选就诊机构(clinicType)自动迁移到新格式的多选(clinicTypes)，糖尿病病齡(yearsWithDiabetes)与共病详情中糖尿病条目的years字段双向同步。

# 基础个人信息与BMI评估规则

---

## 基础字段

| 字段 | 说明 |
|---|---|
| 姓名/称呼 | 如"陳生""張太"，在AI对话中有强制使用规则——AI在回复中只能使用档案中记录的这个称呼，不得使用虚构名字 |
| 年龄 | 整数，岁 |
| 性别 | 男 / 女 / 其他 |
| 身高 | 厘米(cm) |
| 体重 | 支持公斤(kg)和磅(lb)两种单位切换 |
| 体重单位 | kg 或 lb，默认kg |
| BMI | 由身高和体重自动计算，公式：体重(kg) ÷ 身高(m)²。如单位为lb则先换算：体重(kg) = 体重(lb) × 0.45359237 |

---

## BMI分层评估规则

系统根据用户年龄采用不同的BMI评估标准。这反映了老年医学中的一个重要循证结论——"肥胖悖论"(obesity paradox)：大量流行病学研究发现，65岁以上人群中BMI在轻度超重范围的全因死亡率反而最低。长者适度的体重储备提供了对抗感染、手术、急性疾病时的营养缓冲。

### 65岁以上长者糖友标准

| BMI范围 | 分类 | 临床含义 |
|---|---|---|
| < 20.0 | 偏輕消瘦 | 长者体重偏轻可能伴随肌少症或营养不良风险，应避免刻意节食减重，宜补充足够蛋白质与热量。指引：建议维持足够体重储备，预防肌少症与衰弱。 |
| 20.0 – 26.9 | 長者黃金理想 | 符合长者糖友最佳保护区间！适度微胖有助于抵禦疾病消耗、维持肌力与抵抗力。指引：长者适度微胖存活率与抗病力最佳（微胖是福）。 |
| 27.0 – 29.9 | 長者微重 | 体重稍高，建议以规律散步、维持肌力为主，不建议长者进行过度严苛节食。指引：重在"维持肌肉量与日常活力"，不宜盲目追求减重。 |
| ≥ 30.0 | 長者顯著肥胖 | 可能增加膝关节负担及心血管负荷，建议在医生及营养师指导下进行温和调整。指引：建议谘询医护人员进行温和、不流失肌肉的安全体重管理。 |

### 65岁以下成人华人标准（香港卫生署/WHO）

| BMI范围 | 分类 | 临床含义 |
|---|---|---|
| < 18.5 | 體重過輕 | 体重过轻，建议注意均衡营养与热量摄取。 |
| 18.5 – 22.9 | 適中理想 | 身材指标非常理想，请继续保持！ |
| 23.0 – 24.9 | 過重偏高 | 略高于华人成人理想上限，建议适度控制糖分及增加运动量。 |
| ≥ 25.0 | 肥胖指標 | 肥胖会增加胰岛素阻抗，建议逐步调整饮食与运动改善体态。 |

年龄的分界线为65岁——年龄≥65使用长者标准，<65使用成人标准。

# 糖尿病诊断信息与用药管理

---

## 糖尿病诊断信息

| 字段 | 说明 |
|---|---|
| 糖尿病类型 | TYPE_1(1型) / TYPE_2(2型) / GESTATIONAL(妊娠) / PRE_DIABETES(前期) / UNKNOWN(未确定) / OTHER(其他) |
| 其他类型说明 | 当类型为OTHER时的补充文字 |
| 糖尿病病齡 | 年数。与共病详情中糖尿病(DM)条目的years字段双向同步 |
| 胰岛素使用状态 | 布尔值——是否正在注射胰岛素。这同时是一个临床风险标志（见「就诊信息与临床风险标志」） |

---

## 用药清单

系统维护两种格式的用药信息（保持同步）：

**结构化用药清单（主要格式）：** 数组，每个条目包含：
- name：药物名称（中文或英文）
- dosage：剂量（如"500mg""10單位"）
- usage：用法（如"每日早晚各一次，隨餐服"）

**简单字符串（向后兼容格式）：** 所有药物名称以顿号连接的单一字符串。当结构化清单变更时自动更新。

## 三种录入方式

**1. AI拍照识药：** 用户上传药袋/药盒/处方单照片 → 系统通过AI视觉能力识别药物信息 → 识别出的药物自动合并到结构化清单中。合并规则：如果同名药物已存在则更新其剂量和用法，不存在则新增。（详见「药物图片识别服务」）

**2. 从药物名册选择：** 从系统内置的香港HA糖尿专科药物名册中选择（详见「香港HA糖尿专科药物名册」）。选择后以药物的英文通用名/商品名作为name加入清单。

**3. 手动输入：** 用户直接输入药物名称（中文或英文均可），dosage和usage留空待后续补充。

# 共病记录与管理规则

---

## 疾病列表

系统提供以下疾病选项供用户多选：

**常见长期疾病（6种）：** 高血壓(HT) / 糖尿病(DM) / 高膽固醇(CH) / 白內障(CT) / 心臟病(HD) / 中風(ST)

**其他长期疾病（7种）：** 癌症(CA) / 呼吸系統疾病(RD) / 退化性關節炎(OA) / 甲狀腺疾病(TD) / 腸胃疾病(GD) / 肝病(LD) / 其他(OT)

每种疾病有唯一的代码ID和中文标签。

---

## 选择规则

- 用户可多选任意数量的疾病
- 存在一个特殊选项"没有长期疾病"(NONE)——选择NONE时**自动清空所有其他已选疾病**；选择任何疾病时**自动清除NONE**。两者互斥
- 选择"其他(OT)"时，允许用户输入自定义疾病名称（如"痛風""骨質疏鬆"等）

---

## 每种已选疾病的详情

每种已选疾病可记录：
- **患病年数：** 整数
- **详情/备注：** 自由文本（如"服藥控制中""定期專科覆診"等）

---

## 运动习惯

### 三维度输入

**每周运动天数：** 0 / 1-2 / 3-4 / 5+

**每次运动分钟数：** 15 / 30 / 45 / 60+

**运动强度自觉等级：**
- LIGHT（轻度）：轻松无出汗
- MODERATE（中等）：呼吸稍急/微出汗（能说话不能唱歌）
- VIGOROUS（高强度）：剧烈气喘

### ADA标准运动量分类计算规则

系统基于以上三维度自动计算是否达到ADA（美国糖尿病协会）推荐的每周至少150分钟中等强度运动标准：

**天数换算：** 0→0天, 1-2→1.5天, 3-4→3.5天, 5+→5.5天

**总量计算：** 总分钟数 = 换算后天数 × 每次分钟数

**分类规则：**
- 总量 = 0 → NONE（几乎无运动）
- **轻度活动无论总量多少均归为 UNDER_150**——运动生理学的循证结论：轻度活动（无出汗、心跳无明显加快）即使时间长，对胰岛素敏感性的改善效果有限
- 总量 > 0 且 < 150分钟 → UNDER_150（运动不足）
- 总量 ≥ 150分钟 → MET_150（达标）

### 运动类型

多选项列表（8种）：
散步/快步走(WALK) / 深蹲/俯臥撐/阻力訓練(RESISTANCE) / 太極/八段錦/氣功(TAICHI) / 游泳/水中健體(SWIM) / 健身單車/慢跑(CYCLE) / 晨運拉筋/椅子操(STRETCH) / 郊遊遠足(HIKE) / 其他(OTHER)

选择"其他"时可输入自定义运动项目说明。

两个互斥选项：
- **有家人或照顾者日常协助** (hasCaregiverSupport = true)
- **独自照顾自己** (hasNoCaregiverSupport = true)

# AI累积认知与Profile写回机制

---

## 设计理念

系统在每次AI对话后自动提取并累积从对话中获得的患者信息。这个机制映射了临床实践中的**纵向患者理解**——好的家庭医生不是每次看诊都从零了解患者，而是在每次接触中逐步积累对患者的立体理解：他的关切、他的偏好、他最近关心什么主题。

同时，系统区分了**确认的信息**与**AI推论的信息**——这映射了临床记录中 subjective vs objective 的区分。AI的推论（如"这个患者可能有抑郁倾向"）不能等同于患者自己表达的确认信息（如"我最近情绪好差"）。

---

## 累积字段

| 字段 | 类别 | 说明 |
|---|---|---|
| expressedConcerns | 确认 | 患者在对话中明确表达过的关切主题 |
| preferenceSignals | 确认 | 患者表达过的偏好信号（如"重视便利性"） |
| educationTopicsViewed | 确认 | 患者已查看/咨询过的教育主题（避免重复教育） |
| recentQuestionThemes | 确认 | 近期问题的主题（识别关注趋势） |
| inferredNotes | 推论 | AI推论出但未经患者确认的备注（如"怀疑有忧郁倾向""居家支持可能不足"） |
| riskSignals | 推论 | AI检测到的潜在风险信号 |

推论类字段与确认类字段**分开存储**，体现了对AI推论结果的审慎态度——推论不会自动进入AI下次对话的确定性上下文中。

---

## 写回规则

AI每次对话返回的 `extractedProfileData` 中可能包含以下提取字段，写回逻辑为：

| AI返回字段 | 写回目标 | 写回方式 |
|---|---|---|
| statedConcern | expressedConcerns | 追加到数组尾部，去重（已存在则不重复添加） |
| scenarioTheme | recentQuestionThemes | 追加去重 |
| caregiverMentioned (= true) | hasCaregiverSupport | 直接设为 true |
| educationTopic | educationTopicsViewed | 追加去重 |
| preference | preferenceSignals | 追加去重 |
| inferredNote | inferredNotes | 追加去重 |
| riskSignal | riskSignals | 追加去重 |

注意：caregiverMentioned 是一个单向推断——当AI检测到对话中提及了照护者时，自动将 hasCaregiverSupport 设为 true。但反方向（AI没有检测到照护者提及）不会将其设为 false。

# AI决策支持引擎

---

## 定位

AI决策支持引擎是系统的灵魂——它不是一个"会聊天的健康AI"，而是**共同决策(SDM)方法论在糖尿病长者衛教场景中的完整工程化实现**。

引擎的每一个设计决策——从安全门的绝对优先到偏好收集阶段的确定性建议禁令——都有明确的临床伦理或方法论根据。理解这些根据不只是"了解历史"，而是帮助重建者在面对规则未覆盖的边界情况时，做出与方法论一致的判断。

---

## 推理管线流程

当用户发送一条消息时，引擎按以下流程推理：

```
用户消息
    ↓
[1] 安全防护门 (Safety Gate) — 绝对最高优先级
    ├── 检测到急性风险 → 直接输出安全响应，activeNode=1，不进入后续节点
    └── 未检测到 → 继续
    ↓
[2] 场景分类 (Scenario Classification) — Top-2分类
    ↓
[3] 价值澄清判断 (Value Clarification Check)
    ├── 需要价值澄清 + 用户尚未表达偏好 → activeNode=3，返回偏好选择卡片
    └── 不需要 或 已有偏好 → 继续
    ↓
[4] 临床推理 (Clinical Reasoning)
    ├── 动态检索匹配的临床知识条目（13条知识库）
    ├── 结合用户健康档案进行个人化推理
    └── 对偏好敏感决策：盘点选项的Pros/Cons
    ↓
[5] 整合输出 (Integrated Output)
    ├── 纯信息查询 → 极速路径（精简输出）
    └── 决策支持 → 完整的双通道输出（briefVersion + detailedVersion）
```

**关键流程控制规则：**
- 安全门在一切推理之前执行，触发后不进入后续节点
- 场景分类支持同时命中两个场景（Top-2）
- 价值澄清的触发取决于场景类型和查询内容（详见「价值澄清判断逻辑」）
- 偏好敏感问题的强制流程：必须先收集偏好(Node 3)再给建议(Node 5)，不可跳过

---

## 引擎的组成部分

引擎由以下子系统构成，各自有独立的信息域详细描述：

- **安全防护门** — 五重急性风险检测
- **场景分类与路由配置** — 7种场景 + 10个路由节点
- **价值澄清判断** — 决定走教育路径还是SDM路径
- **临床知识库** — 13条循证知识 + 动态检索
- **5-Node推理管线与核心行为准则** — AI的完整行为"宪法"
- **偏好探索与收集机制** — 标准化偏好维度 + 前端-AI契约
- **AI输入输出数据契约** — 数据注入格式 + 输出Schema

[[安全防护门_急性风险检测与应急响应]]
# 安全防护门：急性风险检测与应急响应

---

## 设计原则

安全防护门具有**绝对最高的优先级**——在一切AI推理之前执行。检测到急性风险时，系统不做任何决策辅助，直接输出应急指引和求助资源。

这映射了医学伦理四原则中的**不伤害原则(non-maleficence)**：当患者可能处于生命危险时，一切决策辅助都是次要的，唯一正确的行为是引导患者立即获得专业帮助。

系统将心理健康危机与生理急症置于**同一优先级**，反映了"身心一体"的全人照护理念——糖尿病作为慢性疾病，其心理负担与生理风险同样需要急症级别的安全网覆盖。

---

## 匹配策略

**宽松子串匹配：**
- 将用户输入转为小写后进行子串包含检测（`text.includes(keyword)`）
- 关键词之间为OR关系——命中任何一个即触发
- 大小写不敏感（中文不受影响）

**设计选择：宁可过度触发（false positive）不可遗漏（false negative）。** "我以前試過頭暈但而家冇事"也会触发低血糖警报——在安全场景中，不必要的警告的代价远小于遗漏真正危险的代价。

---

## 五重检测规则

### 第一重：急性低血糖

**触发关键词：** 手震、出汗、心悸、頭暈、昏、意識不清、冒冷汗

**应急响应原文：**
> ⚠️ 偵測到可能嘅緊急低血糖徵狀！請立即食用 15 克糖分（如 3 粒方糖或半罐汽水），15 分鐘後再量血糖。如果徵狀無改善或意識模糊，請立即致電 999 尋求協助。安全第一，暫時唔好依賴 AI 回覆。

**临床背景：** 15:15法则——15克快速碳水化合物（约3粒方糖或半罐含糖汽水），15分钟后重测血糖。这是ADA推荐的标准低血糖急救流程。

### 第二重：DKA/HHS（糖尿病酮酸中毒/高渗性高血糖状态）

**触发关键词：** 口渴難忍、多尿、嘔吐、呼吸有果味、意識模糊、極度疲倦、肚痛

**应急响应原文：**
> ⚠️ 偵測到嚴重高血糖危象（如 DKA 或 HHS）嘅徵象！請立即前往急症室或致電 999 尋求緊急醫療協助。呢種情況需要即時醫院處理，唔好嘗試自行解決。安全第一！

### 第三重：足部感染

**触发关键词：** 傷口不癒合、紅腫發熱、潰瘍、腳痛、腳趾變黑、腳部感染

**应急响应原文：**
> ⚠️ 偵測到可能嘅足部感染或潰瘍！由於糖尿病病友足部問題惡化得好快，請於 24 小時內儘快前往診所或尋求專業醫護處理。暫時請保持傷口清潔，避免再次受壓，但一定要搵專業醫護處理。

### 第四重：心理健康危机

**触发关键词：** 自殺、想死、唔想做人、死咗去、傷害自己、抑鬱、崩潰、絕望、無出口、情緒好差、生無可戀、厭世

**应急响应原文：**
> ⚠️ 偵測到你嘅情緒可能正處於極大壓力或困擾之中。你並不孤單，有人願意陪伴你。請考慮立即致電以下熱線尋求專業支援：
>
> 1. 香港撒瑪利亞防止自殺會：2389 2222
> 2. 生命熱線：2382 0000
> 3. 醫管局精神科 24小時電話諮詢：2466 7350
> 4. 社會福利署熱線：2343 2255
>
> 如果你感到即時生命危險，請立即致電 999。我哋非常關心你嘅安全，請優先尋求專業協助。

### 第五重：高风险档案 + 模糊不适

**触发条件：** 档案中 isInsulinUser=true 或 hasHypoUnawareness=true 或 hasHypoHistory=true，**且**用户输入包含"好唔舒服"或"好暈"或"想嘔"

**应急响应原文：**
> ⚠️ 由於你有相關風險背景且感到明顯不適，建議你暫停使用 AI，儘快聯繫你的家屬或尋求醫療協助。安全第一！

**临床背景：** 对于正在使用胰岛素、有低血糖病史、或有无感低血糖的患者，模糊的不适感可能是低血糖的非典型表现。这些患者的安全阈值更低——宁可过度谨慎。

[[价值澄清判断逻辑]]
# 价值澄清判断逻辑

---

## 设计理念

这是 Ottawa Decision Support Framework (ODSF) 中**决策需求评估(decisional needs assessment)**的工程化——系统判断用户当前面临的是信息需求还是决策需求。

- 信息需求（"什么是糖化血色素"）→ 不需要价值澄清，走**教育路径**——快速输出知识
- 决策需求（"要不要打胰岛素"）→ 需要价值澄清，走**SDM路径**——先收集偏好再给建议

**核心洞察：** 并非所有糖尿病管理问题都是偏好敏感的。低血糖的处理有明确的最佳做法（15:15法则），不需要价值探索。但要不要开始打胰岛素，医学上没有绝对的"最佳"——取决于患者最在意什么。系统精准区分这两类，避免过度介入（对简单查询也做偏好探索）或介入不足（对偏好敏感决策直接给答案）。

---

## 判断规则

### 按场景类型

| 场景 | 是否需要价值澄清 | 理由 |
|---|---|---|
| decision_support_preference | **始终需要** | 偏好敏感决策的定义就是需要价值权衡 |
| medication_side_effect_adherence | **始终需要** | 用药问题往往涉及副作用耐受与疗效的权衡 |
| hba1c_interpretation | **不需要** | 指标解读属于信息教育，不涉及决策 |
| hypoglycemia | **不需要** | 低血糖有明确处理流程，不需要价值权衡 |
| diet_management_questions | **条件触发** | 见下方 |
| general_fallback | **不需要** | 默认走教育路径 |

### 饮食场景的条件触发

当且仅当用户的查询中包含以下**取舍词汇**时触发价值澄清——这些词汇指示用户正在经历内心矛盾，而非单纯索取信息：

**24个取舍词汇完整列表：**
但係、好難、唔想、點算、又想又怕、唔想掃興、煩、想食、矛盾、戒唔到、控制唔到、好難揀、唔好意思、朋友、家人、飲茶、方便、平衡、點揀、邊個好、驚血糖高、又想、又唔想、取捨

**设计精妙之处：** 单纯问"食咩生果好"走教育路径（用户在收集信息），但说"我好想食芒果但又驚血糖高"则进入SDM路径（用户在经历取舍矛盾）。

### 强烈决策特征词（跨场景触发）

无论场景分类结果如何，如果用户查询包含以下15个**强烈决策特征词**则直接触发价值澄清：

要唔要打針、要不要打針、應唔應該打針、唔知打唔打、唔想打針、驚打針、怕痛、要不要打胰島素、應唔應該打胰島素、cgm、連續血糖儀、篤手指定、換藥定打針、點揀好、應唔應該換

## 知识库定位

## 13条知识条目完整原文

### ADA-13：Older Adults Standards (ADA 2026)
> 健康長者 A1C < 7.0–7.5%；中等複雜 < 8.0%；非常複雜避免依賴 A1C。血壓目標 < 130/80 mmHg。建議使用 Statin 預防併發症。

### ADA-6：Glycemic Goals & Hypo (ADA 2026)
> 飯前血糖目標 4.4–7.2 mmol/L。低血糖定義：< 3.9 mmol/L。15:15 法則：15g 糖分，15分鐘後重測。

### ADA-5：Lifestyle Management (ADA 2026)
> 適量帶氧運動與阻力訓練。飲食應均衡，減少加工食品。體重控制有助改善 A1C。

### HK-HB：香港病友篇（地道指南）
> 醣質交換法：1 份醣 = 10g 碳水。進食順序：先湯、菜 -> 肉 -> 飯。糖化血色素 6.5% 以下為理想。

### HA-DIET：醫管局飲食手冊
> 酒樓飲茶：選蒸點（蝦餃、燒賣），避炸點。茶餐廳：選通粉、米粉，走甜、少醬料。1平碗飯 = 5 份醣。

### CHP-DIET：CHP 飲食建議
> 定時定量進食，避免過飽或過飢。選擇高纖維食物（糙米、全麥包）。

### EHS-DIET：長者健康服務指南
> 針對長者口腔與消化力調整。少食多餐。確保攝取充足纖維預防便秘。

### HA-SMART：智友站數據
> 提供水果換算表：細蘋果 1 個 = 1 份醣。注意隱藏糖分陷阱（如芡汁）。

### TCM-HK：中西醫結合指引
> 中藥可作輔助調理，但絕對唔可以自行停咗西藥，因為西藥係直接控制血糖，停咗可能會有急性風險。睇中醫時一定要話比中醫師聽你食緊邊幾種西藥。

### INSULIN-HK：打針（胰島素）心理建設
> 胰島素唔係毒藥，而係身體原本就有但宜家唔夠用嘅「荷爾蒙」。宜家啲針頭好幼（如 4mm），痛感其實比篤手指仲輕。打針有助減輕胰臟負擔，保護剩餘功能。

### MONITOR-PRO：輕鬆監測技巧
> 如果覺得日日量好煩，可以試下「配對監測」：今日量早餐前後，聽日量午餐前後。咁樣可以睇到邊餐飯對你血糖影響最大，唔洗一日量咁多次。

### OUTSIDE-HK：茶餐廳/酒樓選餐進階
> 酒樓：避開糯米雞、粉果、腸粉（皮太厚）。揀點心時食肉唔好食汁。茶餐廳：避開西多士、米線（升糖快）。揀熱檸茶走甜，唔好飲凍飲（多預設糖）。

### FLUCTUATE-HK：血糖波動原理
> 血糖唔係死數，會跟住你食飯、瞓覺、心情變。朝早高可能係因為「黎明現象」（身體準備起身提供能量），或者尋晚食得唔夠。唔好因為一次半次跳動就驚，最重要睇長期趨勢。

# 5-Node推理管线与核心行为准则

本域承载AI决策支持引擎的完整行为"宪法"——包括全局准则、各Node的行为规则、个人化规则、输出编排、以及关键Prompt原文段落。这些内容共同构成了重建者设计AI核心指令(system instruction)的权威参考。

---

## 全局准则

### 角色定位
"專業且極其親切的香港糖尿病決策輔助(PDA)衛教助理"——不是医生、不是决策者，是决策辅助。

### 三不二要

**不改藥** — 只有注册医生可以开具或修改处方。系统严格避免任何可能被解读为处方建议的输出。

**不診斷** — 诊断需要结合病史、体检、实验室检查等多维信息。仅凭文字描述做诊断不仅不专业，还可能导致误诊。系统可以提供"这些症状通常与某某有关"的教育性信息，但不能说"你得了某某"。

**不保證** — 医学具有不确定性，任何治疗方案的结果都是概率性的。保证特定结果不仅不诚实，还可能导致患者在结果不如预期时失去对治疗方案的信心。

**要同理** — 站在患者的生活情境中理解顾虑。怕痛是真实的、担心依赖是合理的、觉得出门带针不方便是实际困难。映射动机式访谈(MI)中"表达同理心"原则。

**要依據** — 建议必须基于最佳可得的临床证据。明确指出建议是基于一般衛教原则还是与患者特定数据相关。通过traceability字段保障可追溯性。

### 语言
地道香港广东话口语——"篤手指""食藥""唔好意思"等。不是普通话翻译成粤语，是真正的粤语表达方式。映射Health Communication中语言匹配(Language Concordance)原则——母语和日常用语呈现的健康信息理解准确度和依从意愿显著提高。

### 4-Layer输出风格
- Layer 1：一句话重点（提炼核心消息）
- Layer 2：核心分析摘要（解释原因与建议）
- Layer 3：方案取捨分析（根据患者价值做Pros/Cons对比）—— PDA的核心输出工具
- Layer 4：建议问诊议题（下次覆诊如何与医生沟通）

### 禁止直接回答清单
由场景匹配到的路由节点的 `do_not_answer_directly` 合并去重得到。

---

## 个人化饮食强制规则

**Prompt原文（规范性参考）：**

> 當病人詢問任何與飲食、水果、外食、正餐、點心、飲茶或運動相關問題時：
> - 【絕對禁止】忽略病人健康檔案中設定的「平時喜歡的食物(favoriteFoods)」與飲食習慣，絕不能丟出千篇一律的通用模板回答！
> - 【必須主動主動呼應並量身定制】：
>   * 例如若檔案中註明病人平時喜歡吃「榴槤」，當病人詢問「食咩生果可以幫我控制血糖？」時，你【必須主動提及並同理病人對榴槤的喜愛】（如：「我知道你平時好中意食榴槤，但榴槤糖分同熱量都比較高，如果想食過下口癮，建議嚴格控制喺一小核以內，最好擺喺兩餐之間食，唔好一次食成房呀！」），同時對比推薦適合控糖的低升糖指數水果（如藍莓、奇異果、蘋果等）以及「一次一個拳頭大」的份量技巧。
>   * 例如若檔案中註明喜歡「叉燒飯、港式奶茶、點心」，詢問外食或主食時，必須主動提供對應的改良技巧（如叉燒去肥少汁、多叫焯菜、奶茶走甜等）。

**方法论根据：** 这是Patient-Centered Care的核心要求。如果系统给出无视患者食物偏好的通用建议，等于说"你的生活不重要，只有医学建议重要"——违背了SDM中"尊重患者自主权"的原则。个人化不是锦上添花，是核心价值承诺。

---

## Node 1：Safety Monitoring（安全监控）

必须最先执行。检测四类急性风险：急性低血糖症状、DKA/HHS/急性并发症、严重足部感染、心理健康/情绪危机。

触发时 activeNode = 1，reply 包含安全警示和求助资源。

完整的检测规则和响应内容见「安全防护门」。

---

## Node 2：Intent Routing（意图分流）

将用户意图划分为五类：
- 数值解读与指标解读
- 饮食与生活习惯建议
- 药物副作用与用药依从性
- 偏好敏感医疗决策（打针/CGM/换药）
- 一般健康知识与医学概念咨询

---

## Node 3：Structured Patient Preferences Exploration（结构化偏好探索）

### 触发条件
面临重大方案抉择或内心抗拒，且用户在历史对话中**尚未表达过偏好**（历史中无"我已選擇我的個人偏好"标志）。

### 行为规则
activeNode = 3，返回 preferenceQuestions（含结构化的偏好选项卡片）。reply 同理长者的抗拒与担忧，亲切引导点选卡片。

### 核心禁令

**Prompt原文（规范性参考）：**

> 在 Node 3（詢問偏好階段），你【絕對不要】輸出具體行動要點（請將 briefVersion.takeHomeMessages 設為空數組 []），也不要輸出 detailedVersion.optionComparison 或給出確定性的治療方案建議！因為此時長者尚未表達個人偏好，直接給出建議違背共同決策(SDM)原則。你必須且只能在長者選擇並提交偏好之後（Node 5），才根據長者的具體偏好量身給出行動要點與建議！

**方法论根据：** IPDAS标准——决策辅助工具不应在患者表达价值观之前呈现倾向性建议。过早给出建议会产生锚定效应(anchoring effect)和框架效应(framing effect)——使患者的后续偏好表达被建议所污染，剥夺患者的决策自主权(decisional autonomy)。

### 标准化偏好维度体系

偏好维度不是随意设计的选项——它们对应PDA文献中通过系统性研究识别出的各类决策场景的核心决策属性(decisional attributes)。完整的维度定义见「偏好探索与收集机制」。

---

## Node 4：Clinical Reasoning & Evidence Retrieval（临床推理与证据检索）

- 基于场景匹配动态检索临床知识条目（见「临床知识库」）
- 结合用户健康档案（年龄、用药、识字程度、照护支持）进行个人化推理
- 对偏好敏感决策（特别是胰岛素和CGM）：必须客观全面盘点两个核心选项的Pros/Cons，结合已表达的偏好权衡各方案对该位长者的实际影响

---

## Node 5：Integrated Output（整合输出）

### 双通道编排规则

**briefVersion.takeHomeMessages（简版重点——高信息密度）：**

*对需要行动的咨询：*
- 2-3条高信息密度量化行动要点
- 每条必须包含**具体数值/份量/频率/时机/品项**（如"每餐主食减至半碗，以糙米/燕麦替代白飯"、"餐後30分鐘快走15-20分鐘"）
- 关键词使用`**加粗**`
- **严格去除废话**——禁止"保持好心情""记得准时吃药"等无量化空话

*对纯知识查询（如"什么是糖化血色素"）：*
- 1-2条核心概念摘要，或直接返回空数组
- 不需要强加行动指引——用户只是在获取知识

**detailedVersion.generalExplanation（详细说明——通俗生活指引）：**
- 通俗生活延伸说明与实用情境贴士
- **禁止堆砌生澀醫學機轉名词**（GLUT-4、SGLT-2阈值、受体敏感性等）——转化为平实易懂的大白话
- **严格禁止复述 briefVersion 中已列出的行动清单**——两个通道职责分明

**detailedVersion.optionComparison（方案利弊）：**
- **日常咨询（饮食/运动/漏服药物/普通波动，占90%场景）：禁止生成**——返回空数组，避免给长者带来不必要的认知负担
- **偏好敏感重大决策（胰岛素/CGM）且已完成偏好选择后：必须生成**——清晰平衡的2个选项Pros/Cons对照

**detailedVersion.suggestedDiscussionPoints（就诊提问建议）：**
- 日常咨询/普通知识查询：0-2条或空数组
- 用药调整/化验异常/重大抉择：2-3条精准、具体、长者能直接唸给医生听的临床提问

### 纯信息查询极速路径

当检测到为纯信息咨询（无价值澄清需求 + 无偏好历史 + 非偏好回应 + 无图片附件）时：
- activeNode 直接设为 5
- 不生成 optionsComparison（空数组）
- briefVersion 提供 3 条高密度要点
- detailedVersion.generalExplanation 专注于通俗实用指引
- 目标：大幅减少输出Token，让长者极速获得答案

---

## 长者阅读优化规则

**Prompt原文（规范性参考）：**

> 1. reply 必須【非常簡短】，一般控制在 2-4 句話內
> 2. 絕對要【分行展示】，積極使用換行符（\n）
> 3. 【稱呼後禁止分行】：例如「老友記，」之後直接連接第一句話
> 4. 所有複雜分析放進 detailedVersion 與 briefVersion
> 5. 【絕對禁止】輸出任何 HTML 標籤（如 \<br/\>），只能使用 \n 換行

**设计根据：** Health Literacy Universal Precautions——默认采用最易理解的方式，而非"检测到低素养才简化"。

## 图片多模态识别指令

当用户在对话中上传图片时，AI被指示进行以下识别：

- **药物/药袋照片：** 精准读取中英文药名、剂量规格、用法及注意事项，用广东话清楚解读，并在detailedVersion中给出日常服用注意细节
- **餐食照片：** 辨识主要食物成分，特别指出碳水化合物/澱粉及隐形糖分，给予升糖指数与份量建议
- **血糖仪/报告照片：** 解读照片中的数值并对比标准范围

当用户只上传图片不附文字时，系统自动使用默认触发文本：
> "請幫我分析這張藥物相片或處方標籤，說明藥物名稱、用法、注意事項及覆診問醫生的問題。"

## 标准化偏好维度体系

这些维度对应PDA文献中各类决策场景已被实证验证的核心决策属性——不是随意设计的问卷选项。

AI在生成偏好问题时，从以下定义的维度中**选择3-4个最相关的**返回给用户，而非每次返回全部维度。选择基于用户查询的具体情境和已知的健康档案信息。

### 针对注射/胰岛素/针剂抉择

| 标签(label) | 价值维度(valueCategory) | 描述(description) |
|---|---|---|
| 注射恐懼與疼痛 | Administration/Pain | 對針頭穿刺的恐懼、怕痛或自我注射困難 |
| 低血糖風險 | Safety | 擔憂發生低血糖急性反應（頭暈、心悸、意識模糊） |

## 前端-AI偏好提交契约

这是一对耦合的业务契约——前端格式化规则与AI Prompt中的检测逻辑必须保持一致。

### 前端组装规则

用户在偏好卡片中选择后，前端将选择组装为以下格式的文本消息发送给AI：

**开头固定标志：** `"我已選擇我的個人偏好（決策考量維度）："`

**每个选择的格式：**
`"- 針對「${questionText}」，我最看重：【${label}】（價值維度：${valueCategory}）"`

**自定义"其他"选项的格式：**
`"- 針對「${questionText}」，我有其他考量：【${customText}】（價值維度：其他）"`

### 星级评分标签

| 星级 | 显示标签 |
|---|---|
| 1星 (⭐) | 一般重視 |
| 2星 (⭐⭐) | 非常重視 |
| 3星 (⭐⭐⭐) | 首要考量 |

### AI端检测逻辑

AI在Prompt中被指示：如果最新用户消息或对话历史中包含 `"我已選擇我的個人偏好"` 这个字符串标志，则判定用户已提交偏好 → activeNode = 5 → 基于偏好量身生成个人化建议。

**关键：** `"我已選擇我的個人偏好"` 是前端与AI之间的触发标志。改动此字符串需同时更新AI的Prompt检测逻辑。

### 验证规则

至少1个有效选择（标准维度选择或有内容的自定义选项）才能提交。无有效选择时提交按钮禁用。

## Profile注入格式

每次AI对话时，用户健康档案被格式化为文本注入AI的推理上下文。关键格式化规则：

**姓名强制使用规则（Prompt原文）：**
> 患者稱呼/姓名: 「${name}」（【極重要】：你在對話、回覆、建議中稱呼或提及病人時，必須且只能使用這個稱呼，例如「${name}」，絕對不要使用其他虛構名字）

**风险标志文本化：** 胰岛素使用→"正在使用胰島素(高風險)"、低血糖史→"有低血糖病史"、体弱→"高齡/體弱個體(需放寬目標)"、无感低血糖→"無感低血糖(極高風險)"、无照护者→"無家人或照顧者協助(獨居高風險，需給予更安全、易操作的個人照護建議)"

**就诊机构代码→中文映射：** GOPC→醫管局家庭醫學門診/普通科門診、SOPC→醫管局專科門診、DHC→地區康健中心/康健站、PRIVATE→私家診所/家庭醫生、OTHER→其他醫療機構、NONE→暫無定期覆診習慣

**运动类型代码→中文映射：** WALK→散步/快步走、RESISTANCE→深蹲/俯臥撐/彈力帶/啞鈴抗阻肌力訓練、TAICHI→太極/八段錦/氣功、SWIM→游泳/水中健體、CYCLE→健身單車/慢跑、STRETCH→晨運拉筋/椅子操/提踵踮腳、HIKE→郊遊遠足

**喜好食物标注：** favoriteFoods字段被标注为"⭐ 患者平時最喜愛的食物 / 偏好"——给AI一个强信号

**识字程度影响：** 低识字时附加指示"如為低識字，請使用更簡短、生活化、口語化且親切的語言"

## 输出结构化Schema

Chat模式下AI返回的完整JSON结构定义：

```
{
  activeNode: INTEGER,                    // 当前激活的推理节点(1-5)
  decisionType: STRING,                   // 决策类型描述
  confidence: NUMBER,                     // 置信度(0-1)
  isLowConfidenceDefaulted: BOOLEAN,      // 低置信度时是否回退为默认行为
  explorationQuestion: STRING,            // 探索性问题(可选)

  preferenceQuestions: [{                  // 偏好选择卡片(Node 3时返回)
    id: STRING,                           // 问题唯一ID
    questionText: STRING,                 // 问题文本
    options: [{                           // 选项列表
      valueCategory: STRING,              // 价值维度代码
      label: STRING,                      // 显示标签
      description: STRING                 // 描述文字
    }]
  }],

  reply: STRING,                          // 主体回复文本

  briefVersion: {
    takeHomeMessages: [STRING]            // 重点速览要点列表
  },

  detailedVersion: {
    optionComparison: [{                  // 方案利弊对照
      option: STRING,                     // 方案名称
      pros: STRING,                       // 优势——AI以换行符(\n)分隔的bullet points格式输出，每行开头加"- "标记
      cons: STRING                        // 顾虑——格式同pros
    }],
    suggestedDiscussionPoints: [STRING],  // 就诊提问建议
    generalExplanation: STRING            // 通俗说明
  },

  suggestedFollowUps: [STRING],           // 推荐追问选项

  traceability: {
    safetyModeTriggered: BOOLEAN,         // 安全模式是否触发
    triggeredNodes: [STRING],             // 触发的节点列表
    currentStep: STRING                   // 当前步骤描述
  }
}
```

所有字段中 `activeNode`、`decisionType`、`confidence`、`isLowConfidenceDefaulted`、`reply`、`suggestedFollowUps`、`traceability` 为必需字段。其余为按需返回。

# 血糖与健康指标记录体系

帮助长者记录、追踪、理解自己的血糖和身体状况数据。

体系包含三个独立但相关的记录维度：
- **血糖记录** — 日常血糖值+多维情境标注+异常判定+统计分析
- **症状记录** — 身体不适症状+专业临床病理分组+统计与就诊摘要
- **糖化血红素(HbA1c)记录** — 长期血糖控制指标+评估区间

血糖记录数据（最近10条）会被注入到AI对话上下文中（注入格式见「AI输入输出数据契约」），使AI能参考最近的数据趋势给出更精准的建议。

所有记录通过本地持久化保存（血糖记录 `dia_glucose`，HbA1c记录 `dia_hba1c`）。

## 血糖异常判定规则

| 条件 | 判定 |
|---|---|
| value < 4.0 mmol/L | 低血糖（不分测量时段） |
| 空腹或餐前 且 value > 7.0 | 偏高 |
| 非空腹非餐前 且 value > 10.0 | 偏高 |
| 其余 | 正常 |
| 无数值但有症状 | 在筛选中归为"异常"类别 |

**阈值的临床依据：** 空腹血糖目标4.4-7.2 mmol/L（ADA-6），餐后通常<10.0 mmol/L。低血糖定义<3.9 mmol/L（ADA标准），系统采用<4.0作为预警阈值提供安全余量。

## 记录保存规则

- 负值自动修正为0
- 值可以为空（纯症状记录，不要求有血糖数值）
- **必须选择测量时段**才能保存
- 支持自定义日期时间（补录历史记录）
- 保存后按时间戳倒序排列（最新在前）

---

## 统计分析逻辑

支持按时间范围（周7天 / 月30天 / 年365天 / 自定义起止日期）动态计算以下指标：

| 指标 | 说明 |
|---|---|
| 平均值(Mean) | 区间内所有有效数值的算术平均 |
| 最高值(Max) | 区间内的最高血糖值 |
| 最低值(Min) | 区间内的最低血糖值 |
| 标准差(SD) | 衡量血糖波动幅度。使用总体标准差——方差计算时除以N（记录总数），而非N-1 |
| 达标率(Time In Range) | 正常次数 ÷ 总有效记录数 × 100% |
| 空腹/餐前平均值 | 仅timeType为空腹或餐前的记录的均值 |
| 餐后平均值 | 仅timeType为餐後2小時的记录的均值 |
| 低血糖次数 | value < 4.0 的记录数 |
| 偏高次数 | 空腹/餐前>7.0 或 其他>10.0 的记录数 |
| 区间内症状次数 | 区间内所有记录的症状总数 |

## 每个预设症状的三层信息

### 面向用户的通俗描述

| 症状 | 通俗描述 |
|---|---|
| 冒冷汗 | 全身發冷、手心出冷汗 |
| 心悸手震 | 手部抖動、雙腳發軟無力，覺得心慌慌、心跳特別快 |
| 頭暈 | 頭重腳輕、看東西天旋地轉 |

### 临床病理分组

| 症状 | 分组 | 分组名称 |
|---|---|---|
| 冒冷汗 | LOW_BG | 低血糖警示群 |
| 心悸手震 | LOW_BG | 低血糖警示群 |
| 頭暈 | LOW_BG | 低血糖/脑供血警示 |
| 極度飢餓 | LOW_BG | 低血糖警示群 |
| 口乾口渴 | HIGH_BG | 高血糖渗透性群 |
| 頻尿 | HIGH_BG | 高血糖渗透性群 |
| 極度疲倦 | HIGH_BG | 代谢利用不良 |
| 視力模糊 | COMPLICATION | 眼底/渗透压警示 |
| 手腳發麻 | COMPLICATION | 周围神经病变警示 |
| 噁心不適 | GENERAL | 消化道/代谢反应 |

自定义症状默认归入GENERAL类别。

### 专业临床说明

| 症状 | 临床说明(clinicalNote) | 临床关注(clinicalConcern) |
|---|---|---|
| 冒冷汗 | 交感神經過度興奮信號，好發於餐前、空腹或活動後 | 提示降糖藥物劑量可能偏大、餐食延遲或未及時加餐 |
| 心悸手震 | 腎上腺素激增早期低血糖預警信號 | 需即時測量血糖，若<4.0需按15-15原則補糖 |
| 頭暈 | 大腦葡萄糖供應不足或血壓波動，注意防跌倒 | 若多發於空腹或起立時，需聯合同步監測血壓與血糖 |
| 極度飢餓 | 下丘腦攝食中樞受刺激，常伴隨低血糖早期 | 評估主食攝入量與進餐間隔時間是否規律 |
| 口乾口渴 | 血漿滲透壓升高刺激口渴中樞，多在餐後或高血糖時加重 | 提示餐後血糖峰值可能過高或全天血糖控制未達標 |
| 頻尿 | 血糖超出腎糖閾引發滲透性利尿 | 關注長者夜尿頻繁帶來的脫水及夜間跌倒風險 |
| 極度疲倦 | 細胞葡萄糖利用不良或血糖大幅波動所致 | 需評估全天血糖波動幅度和基礎代謝狀態 |
| 視力模糊 | 晶狀體滲透壓急性改變引起屈光不正，或微血管病變 | 建議定期安排散瞳眼底檢查，排除糖尿病視網膜病變 |
| 手腳發麻 | 長期高血糖毒性累及周圍神經纖維（對稱性手套襪套樣分佈） | 提示需進行10g單絲觸覺檢查及音叉震動覺篩查 |
| 噁心不適 | 胃腸動力異常、胃輕癱或降糖藥物胃腸道副反應 | 若伴隨血糖極高，需警惕糖尿病酮症酸中毒(DKA) |

---

## 症状统计逻辑

按时间范围（周/月/年/自定义）动态计算：

- **四大分组次数汇总：** 低血糖群(LOW_BG)、高血糖群(HIGH_BG)、神经微血管(COMPLICATION)、一般(GENERAL)各自的总发生次数
- **每个症状的统计：** 出现频次、占总症状次数的百分比、高发时段（在哪个timeType下最常出现）
- **总体统计：** 有症状的记录总笔数、总症状人次

---

## 自动生成就诊摘要

系统基于统计数据自动生成一段门诊主诉摘要文字，规则：

- 无记录时：`"患者近期暫無自覺不適或症狀紀錄。"`
- 有记录时包含：
  - 累计不适记录笔数和症状人次
  - 所有已记录症状按出现频次降序排列，取前3个高频症状，列出其排名和高发时段
  - 若低血糖相关症状>0次：建议排查降糖药物剂量或延迟进餐
  - 若高血糖症状>0次：建议评估餐后血糖峰值
  - 若并发症症状>0次：建议安排下肢触觉与眼底检查

# 糖化血红素(HbA1c)记录与评估

---

## 数据模型

| 字段 | 类型 | 说明 |
|---|---|---|
| id | 字符串 | 唯一ID（时间戳） |
| value | 字符串 | HbA1c数值（%） |
| date | 字符串 | 检查/抽血日期（YYYY-MM-DD） |
| timestamp | 数字 | 用于排序的时间戳 |

---

## 四档评估区间

| HbA1c范围 | 评估 | 说明 |
|---|---|---|
| < 6.0% | 非糖尿病/非常理想 | — |
| 6.0% – 6.9% | 控制良好 | 一般长者目标<7.0% |
| 7.0% – 7.9% | 尚可 | 部分高龄或有并发症长者目标可放宽至<8.0%，遵循医嘱 |
| ≥ 8.0% | 偏高 | 需配合医生调整药物与饮食方案 |

**临床背景：** HbA1c反映过去2-3个月的平均血糖水平。ADA对老年糖尿病患者实行A1C目标分层管理——健康长者<7.0-7.5%，中等复杂度<8.0%，非常复杂的避免过度依赖A1C（知识库ADA-13）。

# 用药提醒体系

---

## 数据模型

**提醒项(ReminderItem)：**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | 字符串 | 唯一ID |
| name | 字符串 | 药物名称 |
| dosage | 字符串 | 剂量（如"500mg""1粒"） |
| period | 枚举 | morning / noon / evening / bedtime |
| active | 布尔 | 是否启用 |

**服药记录：** 键值格式 `${YYYY-MM-DD}_${提醒ID}` → 布尔值（true=已服药）

---

## 四时段定义

| 时段 | 时间范围 | 中文标签 |
|---|---|---|
| morning | 05:00 – 11:59 | 早上/早餐後 |
| noon | 12:00 – 16:59 | 中午/午餐後 |
| evening | 17:00 – 20:59 | 晚上/晚餐後 |
| bedtime | 21:00 – 04:59 | 睡前 |

---

## 每日自动重置

服药记录的键值包含日期——新的一天（新的YYYY-MM-DD）自动产生全新的空白记录。无需额外的重置操作。

---

## 从Profile匯入

从用户档案的结构化用药清单(medicationDetails)一键匯入。匯入时根据每种药物的usage字段中的关键词**自动推测时段**：

| 关键词 | 推测时段 |
|---|---|
| 含"晚""夜""pm" | evening |
| 含"中""午""12" | noon |
| 含"睡" | bedtime |
| 其他（包括usage字段为空的情况） | morning |

**匯入去重规则：** 如果提醒列表中已存在相同name+period的条目则不重复添加。

**独立存储：** 匯入后，提醒列表(reminders)与档案药物清单(medicationDetails)独立存储、独立演化。修改档案中的药物信息不会自动同步到提醒列表。

---

## 自动提醒触发

**触发条件（三个条件同时满足）：**
1. 当前时段有启用的(active=true)提醒项
2. 这些提醒项中有尚未登记服药的（服药记录中对应键值不存在或为false）
3. 当日该时段尚未自动触发过（使用本地存储标记 `dia_auto_triggered_${日期}_${时段}` 判断去重）

**触发行为：**
- 标记该时段当日已触发（防止重复弹出）
- 弹出提醒界面
- 广东话(zh-HK)语音播报（语速0.85——专为长者放慢），内容包含未服药物名称列表和温馨提醒用温水送服

---

## 服药登记与追踪

- 逐药登记：点击某药物标记为已服药，再点击可撤销
- 一键全部服药：标记当前时段所有未服药物为已服，语音播报祝贺
- 完成度计算：已服数 ÷ 当日启用的提醒总数
- 全部服妥时的正向反馈（鼓励长者积极配合用药）

---

|---|---|---|

| 達美康 Diamicron (格列齊特) | 80mg | morning |
| 捷諾維 Januvia (西格列汀) | 100mg | morning |
| 適糖達 Jardiance (恩格列淨) | 10mg | morning |
| 庫魯糖 Glucophage | 500mg | evening |
| 胰島素注射 Insulin | 10單位 | morning |

---

## 持久化

提醒列表存储键：`dia_reminders_v2`
服药记录存储键：`dia_taken_logs_v2`

[[问诊备忘与就诊准备体系]]
# 问诊备忘与就诊准备体系

系统的终极价值承诺的"最后一公里"——确保AI帮助长者建立的知情度和价值清晰度，能够在最终的医患面对面场景中被有效传递。

本体系管理的核心数据字段——savedDoctorQuestions（保存的问诊问题列表）、nextClinicQuestions（下次问诊清单）、nextClinicDate（下次问诊日期）——存储于用户健康档案中（详见「就诊信息与临床风险标志」中的问诊准备数据字段）。

---

## 问题保存机制

### 保存来源

**来源一：AI对话中的有价值内容**
- briefVersion.takeHomeMessages中的每条要点可被保存
- detailedVersion.suggestedDiscussionPoints中的每条问题可被保存
用户通过点击"保存"操作将选中的内容加入问题列表。

**来源二：用户手动新增**
支持手动输入（键盘或语音）。提供4个预设灵感问题供参考：
1. "想向醫生請教服藥時間可否配合生活作息調整？"
2. "最近服藥後有些腸胃不適，是否有替代方案？"
3. "想諮詢下次化驗是否需要加驗糖化血色素或腎功能？"
4. "平時血糖波動較大，是否適合使用連續血糖儀 (CGM)？"

### 保存规则
- 新的问题添加到列表最前面
- 与已有问题合并去重（相同文本不重复添加）
- 存储在档案的 savedDoctorQuestions 字段中

---

## AI智能总结

### 功能
输入全部已保存的问题列表，AI归纳出高频关注类别和精选建议问诊问题。

### AI总结的规则要求
- 统计并归纳长者最关心的3至5个核心类别话题，按出现频率排序
- 简短说明每个类别的主要关注点
- 根据类别重点精炼出3至5个最实用、切中要害、可直接向医生开口发问的广东话问题
- 整体摘要使用亲切的香港广东话口语，2-3句概述
- 文字精简、不囉嗦

### 输出结构
- **summary**：整体概述（繁体中文广东话口语，2-3句）
- **categories**（3-5个）：每个包含 categoryName（类别名称）、description（简要说明）、frequency（频率标签如"最常提問""高頻關注""經常諮詢"）
- **recommendedQuestions**（3-5个）：每个包含 question（建议直接问医生的广东话问题句子）、categoryTag（所属类别标签）

### API失败时的Fallback数据

**预设3个类别：**
1. 降糖用药与反应 —— 关心食药后的胃胀、低血糖风险及是否需调药（高频关注）
2. 饮食份量与外食 —— 关注外出饮茶、澱粉水果份量与饭后血糖升幅（经常咨询）
3. 日常血糖波动与指标 —— 关注空腹与餐后血糖差距及糖化血色素达标情况（持续追踪）

**预设3个建议问题：**
1. "醫生，我食完降糖藥之後有時覺得胃部唔適，想問下係咪正常反應？需唔需要調整？"（用药反应）
2. "醫生，我食某些食物（例如生果或澱粉類）之後血糖升得較急，份量應該點控制？"（饮食控制）
3. "醫生，呢度係我最近記錄嘅血糖數值，想問下我目前嘅血糖波動算唔算理想？"（血糖波动）

---

## 下次问诊清单管理

### 来源
**来源一：** 从AI总结的推荐问题中挑选
**来源二：** 用户自定义新增（自定义问题同时自动加入savedDoctorQuestions）

### 同步规则
- 编辑一个问题的文本时，如果它同时存在于savedDoctorQuestions和nextClinicQuestions中，两处同步更新
- 删除一个问题时，同时从两个列表中移除

---

## 问诊日期提醒

### 存储格式
YYYY-MM-DD

### 倒计时状态计算

| 状态 | 条件 | 显示 |
|---|---|---|
| TODAY | 日期 = 今日 | "今日！"（高优先级醒目提醒） |
| FUTURE | 日期 > 今日 | "還有 N 日" |
| PAST | 日期 < 今日 | "已過期" |
| NONE | 未设定日期 | "未設定問診日期" |

### 首页同步
- nextClinicQuestions 和 nextClinicDate 在首页同步展示
- 当日(TODAY)时在首页以高优先级醒目方式提醒——"今日係您預定的問診覆診日！記得帶齊血糖紀錄與問診清單！"

---

## 信息提炼链路

完整的从AI对话到诊室的信息提炼链路：

```
AI对话产出原始建议（takeHomeMessages / suggestedDiscussionPoints）
    ↓ 用户选择性保存
savedDoctorQuestions（保存有价值的问题）
    ↓ AI分析归纳

    ↓ 用户精选最重要的
nextClinicQuestions（下次问诊清单）
    ↓ 就诊日期到来
长者带着整理好的清单走进诊室
```

# 引导流程(Onboarding)

---

## 触发条件
档案中 age（年龄）为空 **或** gender（性别）为空时，系统进入引导流程而非首页。

---

## 两步流程

### Step 1：基本资料与身材指标
- **必填：** 年龄、性别
- **选填：** 姓名/称呼、身高、体重（填写后自动计算BMI并显示分层评估）

- 糖尿病类型选择

# 数据持久化策略

---

## 核心原则

各业务数据被妥善本地持久化，确保同设备下次打开时所有数据完整可见。

---

## 存储键值映射

| 存储键 | 数据内容 | 保存时机 |
|---|---|---|
| dia_profile | 用户健康档案完整数据 | 每次档案变更后 |
| dia_glucose | 血糖记录数组 | 每次记录变更后 |
| dia_hba1c | HbA1c记录数组 | 每次记录变更后 |
| dia_large_font | 大字模式开关 | 切换时。默认值 true |
| dia_reminders_v2 | 用药提醒列表 | 每次变更后 |
| dia_taken_logs_v2 | 服药记录 | 每次登记后 |
| dia_chat_messages | AI对话历史 | 每次消息更新后 |
| dia_auto_triggered_${日期}_${时段} | 用药提醒自动弹窗去重标记 | 自动提醒触发时 |

---

## 特殊持久化规则

**对话历史保存时的图片剥离：** 保存到本地存储时，消息中的图片附件会被剥离——保留 mimeType 和 name 但清空 base64 和 previewUrl。这是防止本地存储溢出的优化。后果是重新加载页面后图片预览不可用，但对话文字完整保留。

**档案加载时的向后兼容数据迁移：**
- 旧格式的单选就诊机构(clinicType) → 自动迁移到新格式的多选(clinicTypes)
- yearsWithDiabetes 与 conditionDetails.DM.years 双向同步
- 旧数据缺失新字段时赋予默认值

# 语音输入能力

## 业务需求

系统支持**广东话(zh-HK)语音输入**作为文字键入的替代方式，服务于长者可能不擅打字的需求。

## AI转写路径

通过AI实现高精度的语音转文字：

1. 通过浏览器的 MediaRecorder API 录制用户语音
2. 录音完成后将音频数据转为 base64 编码

5. 填入时在光标位置插入文字，并触发输入事件确保状态同步

# 旧项目UI设计理念与长者友好设计

---

## 整体设计语言

旧项目采用温暖、柔和、高信任感的视觉风格，面向香港长者用户群体：

**品牌色系：**
- 主色 #4A6E85（沉稳蓝灰）——传递专业与可信赖
- 辅色 #7FA0B4（柔和天蓝）——传递亲切与温暖
- 点缀色 #E8DED2（暖米色）——传递舒适与家庭感
- 背景 #FBFBFA（几乎纯白的微暖底色）

**字体：** Noto Sans HK——香港用户群体的中文字体选择，支持繁体中文和粤语特有字符。

**设计圆角：** 大圆角(1.75rem)为主，营造柔和无棱角的视觉感受——对长者用户更友好，减少界面的"技术感"。

---

## 长者友好的核心设计决策

**大字模式默认开启：** 系统默认 isLargeFont = true。CSS通过 `.large-font` 类实现全局字体放大——从 `text-xs`(→16px) 到 `text-5xl`(→36px) 各级别都有对应放大，按钮最小高度不低于56px。这是Health Literacy Universal Precautions的直接体现——不需要用户主动开启，系统默认就是长者友好的。

**Emoji作为视觉锚点：** 大量使用emoji（🩸💊🤒📋⏰等）作为功能区块的视觉标识——长者在密集的文字信息中可以通过emoji快速定位目标区域，降低认知搜索成本。

**广东话口语贯穿文案：** 所有界面文案使用地道广东话而非标准书面语。例如"篤手指"而非"指尖采血"，"食藥"而非"服用药物"。这不只是翻译——是真正从粤语使用者的日常用语出发设计的文案。

**低认知负荷的信息分层：** AI回复采用"主体简短(2-4句) + 详细说明可展开/收起"的架构——长者默认看到的是精简信息，需要深入时再展开。减少信息过载。

**触控友好：** 大字模式下所有可交互元素（按钮、输入框、选择器）最小高度56px，确保长者手指不容易误触。

---

## 导航结构

底部固定导航栏，4个入口：首頁(🏠) / 血糖紀錄(🩸) / 問題紀錄(📝) / 個人檔案(👤)。

引导流程(Onboarding)期间不显示导航栏。

全局悬浮麦克风按钮固定在右下角——三态视觉反馈：待机(蓝色) / 录音中(红色呼吸灯) / 处理中(灰色旋转)。

# 核心业务逻辑与壳的接口特征

本域描述核心业务逻辑对UI壳的需求——无论壳是什么形态，都需要满足这些接口需求。这些不是UI的具体实现方式，而是业务逻辑向壳提出的"我需要你做到什么"的需求边界。

---

## AI输出驱动UI行为

AI返回的 `activeNode` 字段决定了UI需要渲染什么类型的内容：

| activeNode | UI需要做什么 |
|---|---|
| 1 | 渲染安全警示区域——醒目的紧急提示 + 求助资源（电话链接等） |
| 3 | 渲染偏好选择交互——呈现 preferenceQuestions 中的选项卡片，支持用户多选+自定义+星级评分，收集后组装为格式化文本发送 |
| 5 (或非1非3) | 渲染完整的AI回复——主体文本 + 重点速览(briefVersion) + 可展开的详细说明(detailedVersion) + 就诊提问建议 + 追问建议 |

---

## briefVersion与detailedVersion的展示架构

旧项目的信息展示架构（供参考，重建者可以设计完全不同的呈现方式）：

- **主体回复(reply)**：始终可见，作为对话气泡的主要内容
- **重点速览(briefVersion.takeHomeMessages)**：始终可见，紧接主体回复下方，每条要点支持"保存到问诊备忘"操作
- **详细说明(detailedVersion)**：默认收起，用户点击展开——包含 generalExplanation（通俗说明）和 optionComparison（方案利弊表）
- **就诊提问(suggestedDiscussionPoints)**：默认收起，用户点击展开——每条问题支持"保存到问诊备忘"操作
- **追问建议(suggestedFollowUps)**：在最后一条AI消息下方显示为可点击的快捷按钮，点击即发送该追问

---

## 偏好卡片的交互模式

旧项目的偏好收集交互模式（供参考）：

- 每个偏好选项呈现为一张卡片——显示icon、label、description
- 支持多选——点击选中/取消
- 提供"其他个人考量"选项——展开后可输入自定义文字
- 底部有"确认提交"按钮——至少选择1项才能启用
- 提交后将选择组装为格式化文本发送给AI（格式见核心文档集「偏好探索与收集机制」）

---

## optionComparison的Pros/Cons文本解析

AI返回的 optionComparison 中 pros 和 cons 字段是以换行符(`\n`)分隔的多行文本，每行是一个bullet point（行首带"- "标记）。前端需要将其解析为列表项显示。解析规则：

1. 将文本中的 `\n` 替换为实际换行
2. 按换行分割为多行
3. 每行去除头部的bullet标记（`•`、`-`、`*`、`▪`、`●`等）和编号（`1.`、`(1)`、`①`等）
4. 过滤掉空行
5. 每行作为一个独立的列表项显示

---

## 原始System Instruction的大致组织结构

以下是旧项目中AI对话核心system instruction的大致组织结构，供重建者设计Prompt时参考。在Gemini等模型中，system instruction中信息的排列顺序可能影响AI的遵守优先级（通常越靠前优先级越高）。

```
1. 角色定位与整体身份声明
2. 长者阅读与排版优化规则（reply简短/分行/禁HTML等）
3. 图片多模态识别指示（如有图片附件）
4. 5-Node专家流程控制与行为准则
   4a. 个人化饮食强制规则（含示例）
   4b. Node 1 Safety Monitoring
   4c. Node 2 Intent Routing
   4d. Node 3 Structured Preferences Exploration（含标准化维度定义+核心禁令）
   4e. Node 4 Clinical Reasoning
   4f. Node 5 Integrated Output（含双通道编排规则+输出策略）
5. 纯信息查询极速路径优化（条件触发时追加）
```

紧随system instruction之后的用户prompt中包含：
```
1. 患者完整健康档案（formatUserProfileSummary）
2. 动态检索到的临床知识条目
3. 最近10次血糖数据
4. 最新用户消息
5. 对话历史
6. 偏好敏感问题的特别提醒（强制触发规则）
```

此结构仅供参考——重建者可根据所使用的AI服务的特性调整组织方式。

# 灰色地带标注与边界讨论

以下是在核心业务逻辑与壳之间存在模糊边界的信息项。它们在核心文档集中已按"宁多勿漏"原则纳入（或标注），此处展开讨论其灰色性质，帮助重建者在面对不同UI形态时做出判断。

## 大字显示模式

**核心文档集中的处理：** 作为业务需求纳入——"系统提供适合长者阅读的大字显示模式，且默认开启"。

**灰色讨论：** "支持大字模式"是面向长者用户群的无障碍业务需求——壳变换到电视屏幕App时同样需要。但具体的字体放大比例（CSS中 text-xs→16px 等）是视觉实现选择。"默认开启"这个决策值是业务规则——它体现了Health Literacy Universal Precautions的设计哲学。

**重建者建议：** 保留"大字模式默认开启"这个业务决策。具体的放大规则根据新UI的设计语言重新设计。

## 广东话语音播报（用药提醒）

**核心文档集中的处理：** 纳入用药提醒的自动提醒规则中——触发时进行广东话语音播报，语速0.85。

**灰色讨论：** "用语音提醒长者服药"是业务需求（长者可能不总是看着屏幕，语音提醒能穿透注意力）。但使用Web Speech API的speechSynthesis实现是技术选择。语速0.85的具体数值也可能因语音引擎不同而需要调整。

**重建者建议：** 保留"广东话语音播报"这个业务行为，但语音技术方案和语速参数根据实际技术环境调整。

## 对话历史的持久化

**核心文档集中的处理：** 在数据持久化策略中记录了对话历史的保存（`dia_chat_messages`）和图片剥离规则。

**灰色讨论：** "对话在浏览器会话间保持"是UX选择还是业务需求？如果用户关闭浏览器后再打开期望看到之前的对话——这更偏向UX体验。但如果AI的累积认知依赖于对话历史的保持（如偏好表达的检测依赖历史中是否包含"我已選擇我的個人偏好"）——那持久化就有业务功能上的必要性。

**重建者建议：** 建议保留对话持久化——至少在同一个会话周期内。是否跨浏览器会话保持可以根据产品需求决定。注意偏好检测逻辑对对话历史的依赖。

## 数据上报在Chat模式下的触发

**核心文档集中的处理：** 在数据上报服务中标注——当前仅在Guided模式结果页自动触发，Chat模式下不自动上报。

**灰色讨论：** 这可能是设计意图（Chat模式数据量大、对话次数多，每次都上报不合理），也可能是功能迁移未完成（系统从Guided模式迁移到Chat模式时未更新上报逻辑）。

**重建者建议：** 根据产品需求确认Chat模式是否需要上报机制。如果需要，考虑设计一个合理的触发时机（如用户主动触发、或达到一定对话轮次后提示上报）。

## 路由节点中的safety_trigger_keywords

**核心文档集中的处理：** 在场景分类与路由配置中标注为"配置性数据"——当前系统中安全检测的实际逻辑完全在安全防护门中实现，路由节点中的safety_trigger_keywords未被代码使用。

**灰色讨论：** 这些关键词可能是预留的设计——未来可能将安全检测与路由配置更紧密地耦合。也可能是过时的配置——安全门独立化后这些字段变得冗余但未被清理。

**重建者建议：** 安全检测逻辑以「安全防护门」中的规则为准。路由节点中的safety_trigger_keywords可以忽略或保留作为参考数据。

## 症状列表的命名不一致

**事实：** PREDEFINED_SYMPTOMS中使用"心悸手震"作为一个合并症状项，但SYMPTOM_DETAILS（面向用户的通俗描述）中没有"心悸手震"这个key——它有"手震"和"心跳加速"两个独立key。同样"手腳發麻"在PREDEFINED_SYMPTOMS中存在但在SYMPTOM_DETAILS中没有对应key。

**影响：** 这是代码中的微小不一致，可能是迭代过程中产生的。业务定义以PREDEFINED_SYMPTOMS和SYMPTOM_CLINICAL_CATEGORIES为权威来源（两者一致），SYMPTOM_DETAILS是UI展示辅助信息。

**重建者建议：** 以核心文档集中的10种预设症状列表和临床病理分组为准。面向用户的通俗描述可以重新设计以确保与症状名称一一对应。
