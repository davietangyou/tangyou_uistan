# 线上服务托管实例（systemd）

版本：1.2

---

## 0. 文档使用说明

本文档是 `tangyou_uistan` 在自托管 Linux 服务器上，从零搭建 systemd 服务托管的完整依据。它可以用于三种场景：

- 在一台全新机器上从零搭建；
- 在已有机器上核对当前配置；
- 日常运维与故障排查时作为事实来源。

本文档是自足的：搭建所需的信息、精确文件、命令、预期输出、故障判读与验收清单都在本文档内，不依赖其他 systemd 通用文档。

本文档覆盖：操作系统与运行时检查、用户与目录准备、代码与依赖、`.env.local`、systemd unit、启动与验收、故障排查、日常运维、已知边界、从零复现清单。

本文档不覆盖：上层反向代理/TLS/DNS 的配置、Google AI Studio 预览环境、应用业务逻辑、`GEMINI_API_KEY` 的实际值。

## 1. 目标服务概览

`tangyou_uistan`（糖友導航）是一个面向香港糖尿病长者的 AI 辅助衛教与决策支持 Web 服务。它的运行时链路如下：

```
浏览器
  → https://tangyou-app.alphathought.org/
  → 上层 nginx / CDN（不在本文范围）
  → 127.0.0.1:9002
  → /usr/bin/npm run dev
  → tsx server.ts
  → Vite middleware + /api/gemini/*
```

正式域名目前由 Cloudflare Workers 的 Route 承接（见《线上无服务器部署实例（Cloudflare Workers）.txt》），上面这条链路是 Route 之下的旧源站，作为备用渠道保留。Route 模式下 DNS 未改动：在 Cloudflare 一侧撤下该主机名的 Route，流量即回到本实例；本实例自身的验收以 `127.0.0.1:9002` 为准。

关键参数：

| 项 | 值 |
| --- | --- |
| unit 名 | `tangyou_uistan.service` |
| 运行用户 | `webser` |
| 主组 | `webgp` |
| 工作目录 | `/da04/webser/sour/pro/tangyou_uistan_0` |
| 启动命令 | `/usr/bin/npm run dev` |
| 监听端口 | `9002`（由 `.env.local` 的 `PORT=9002` 指定） |
| 健康端点 | `http://127.0.0.1:9002/api/health` |
| 应用日志 | `/da04/webser/logs/pro/tangyou_uistan_0.log` |
| 运行模式 | dev（Vite middleware，非生产构建） |

### 1.1 为什么使用 systemd

从 SSH 会话直接启动的进程，通常会随会话结束而收到挂断信号；`nohup` 对多层工具链的保护并不可靠；`setsid` 只能解决会话脱离，不能提供重启、开机自启与统一观测。systemd 把服务放入独立的 cgroup，使它与登录会话解耦，并提供重启策略、日志、退出码与开机集成。

本文档搭建的服务位于 `system.slice/tangyou_uistan.service`，不依附于任何 `session-*.scope`。

### 1.2 进程存活与业务可用

systemd 能判断进程是否存活；业务是否可用需要 `/api/health` 与浏览器端冒烟来确认。本文档的验收会同时覆盖这两层。

## 2. 前置条件与环境检查

### 2.1 目标环境

| 项 | 当前参考值 | 检查命令 |
| --- | --- | --- |
| 操作系统 | Debian GNU/Linux 12（内核 `6.1.0-41-cloud-amd64`） | `cat /etc/os-release`、`uname -r` |
| systemd | Debian 12 对应 252 系列；精确版本以现场为准 | `systemctl --version` |
| Node | `/usr/bin/node` v22.21.0 | `node -v`、`which node` |
| npm | `/usr/bin/npm` | `npm -v`、`which npm` |
| 数据盘 | `/dev/sdc` 挂载于 `/da04` | `findmnt /da04`、`df -h /da04` |
| 运行用户 | `webser`，主组 `webgp` | `getent passwd webser`、`id webser` |
| 出站网络 | 可访问 Gemini API 目标域名 | 健康端点、应用日志 |

新机器上的 UID/GID 可以与参考值不同；关键是用户名 `webser`、组名 `webgp` 存在，并且 `webser` 的主组是 `webgp`。

### 2.2 用户与组

当前参考形态：

```
webser:x:1003:1006::/da04/webser:/bin/bash
uid=1003(webser) gid=1006(webgp) groups=1006(webgp),1000(google-sudoers)
```

若新机器尚无对应用户与组，一种创建形态是：

```bash
sudo groupadd webgp
sudo useradd -m -d /da04/webser -g webgp -s /bin/bash webser
# 可选：把 webser 加入 sudo 组（组名视发行版而定）
sudo usermod -aG google-sudoers webser
```

`google-sudoers` 是 Google Cloud 镜像中的组名；其他环境可使用 `sudo`、`wheel` 或对应的管理员组。用户 home `/da04/webser` 也用于 npm 缓存与用户级配置。

### 2.3 数据盘与目录

当前项目与日志位于 `/da04` 数据盘。新机器上可以沿用 `/da04`，也可以使用其他挂载点；若挂载点不同，本文档中所有 `/da04/...` 路径都需要同步替换。

需要存在的目录：

```bash
/da04/webser/logs/pro
/da04/webser/sour/pro/tangyou_uistan_0
```

检查：

```bash
findmnt /da04
ls -ld /da04/webser /da04/webser/logs /da04/webser/logs/pro /da04/webser/sour/pro
```

### 2.4 Node 与 npm

当前服务通过 `/usr/bin/npm` 启动，`npm run dev` 内部调用 `tsx server.ts`。`/usr/bin/npm` 的 shebang 使用 `/usr/bin/env node`，因此 `node` 需要出现在 systemd 的默认 PATH 中。

两种常见形态：

- 使用系统 Node（当前形态）：`/usr/bin/node`、`/usr/bin/npm`，systemd 默认 PATH 已覆盖。
- 使用 nvm 管理的 Node：systemd 不读取 `.bash_profile`，需要在 unit 中显式设置 PATH，或改用 `bash -lc`。本文档以系统 Node 为参考形态。

检查：

```bash
which node
node -v
which npm
npm -v
```

## 3. 准备项目目录与代码

### 3.1 同步代码

把 `tangyou_uistan` 项目代码放到：

```
/da04/webser/sour/pro/tangyou_uistan_0
```

项目根目录应包含 `package.json`、`server.ts`、`server/`、`public/styles/app.css`、`domain/`、`services/`、`views/`、`components/`、`hooks/`、`utils/` 等。当前托管形态是 `npm run dev`（Vite middleware），页面皮肤与大字规则依赖仓库内的 `public/styles/app.css`；该文件不在时，Tailwind 工具类仍可用，但自定义样式会丢失。

### 3.2 调整属主

项目目录与日志目录的运行属主为 `webser:webgp`：

```bash
sudo chown -R webser:webgp /da04/webser/sour/pro/tangyou_uistan_0
sudo chown -R webser:webgp /da04/webser/logs/pro
```

### 3.3 安装依赖

在项目根目录执行：

```bash
cd /da04/webser/sour/pro/tangyou_uistan_0
sudo -H -u webser npm ci --prefer-offline --no-audit --no-fund
```

`package-lock.json` 已与 `package.json` 对齐，正常情况直接使用 `npm ci`，并以 `webser` 身份安装，以免 `node_modules` 属主与运行用户不一致。若 `npm ci` 因 lockfile 不同步失败，可以改用 `sudo -H -u webser npm install`，并单独评审 `package-lock.json` 的变化。

检查：

```bash
ls -ld node_modules
node -e "console.log(require('./package.json').scripts.dev)"
```

预期 `scripts.dev` 为 `tsx server.ts`。

可以从仓库内的 `.env.example` 复制后再填写真实密钥：

`server.ts` 启动时经 `server/env.ts` 按以下顺序读取环境变量，且不覆盖已存在的进程环境变量：

进程环境变量 ＞ .env.server.local ＞ .env.local ＞ .env

## 5. 创建 systemd unit

### 5.1 unit 文件全文

部署路径：

```
/etc/systemd/system/tangyou_uistan.service
```

全文：

```ini
[Unit]
Description=tangyou_uistan (npm run dev)
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=0

[Service]
Type=simple
User=webser
WorkingDirectory=/da04/webser/sour/pro/tangyou_uistan_0
ExecStart=/usr/bin/npm run dev
Restart=always
RestartSec=3
TimeoutStopSec=10
StandardOutput=append:/da04/webser/logs/pro/tangyou_uistan_0.log
StandardError=append:/da04/webser/logs/pro/tangyou_uistan_0.log

[Install]
WantedBy=multi-user.target
```

### 5.2 字段说明

| 字段 | 当前选择 | 作用 |
| --- | --- | --- |
| `Description` | `tangyou_uistan (npm run dev)` | 标识服务与运行模式 |
| `After` / `Wants` | `network-online.target` | 网络就绪后再启动 |
| `StartLimitIntervalSec` | `0` | 关闭启动频率限制，允许持续重启 |
| `Type` | `simple` | npm 作为主进程，启动后即视为已启动 |
| `User` | `webser` | 以 webser 身份运行 |
| `WorkingDirectory` | 项目根目录 | 决定相对路径与 `.env.local` 读取位置 |
| `ExecStart` | `/usr/bin/npm run dev` | 绝对路径启动，不经过 shell 展开 |
| `Restart` | `always` | 正常退出与异常退出都会重启 |
| `RestartSec` | `3` | 重启间隔 3 秒 |
| `TimeoutStopSec` | `10` | 停止等待 10 秒，超时升级 SIGKILL |
| `StandardOutput/Error` | `append:` 日志文件 | 应用输出写入同一文件 |
| `WantedBy` | `multi-user.target` | 开机自启 |

### 5.3 几个关键取舍

**没有写 `Group=`**

`User=webser` 时，systemd 会从 passwd 读取 `webser` 的主组 `webgp`。显式写 `Group=webser` 要求系统中存在名为 `webser` 的组；若不存在，会出现 `216/GROUP`。当前 unit 采用省略 `Group=` 的形态。

**没有写 `Environment=HOME` / `Environment=PATH`**

systemd 会按 passwd 设置 `HOME=/da04/webser`，并使用默认 PATH（包含 `/usr/bin`）。`/usr/bin/npm` 与 `/usr/bin/node` 因此可被解析。若新机器使用 nvm 管理的 Node，需要显式设置 PATH 或改用 `bash -lc`。

**`ExecStart` 使用绝对路径**

`/usr/bin/npm run dev` 直接由 systemd 执行，不经过 shell。这样进程树是 `npm → sh → tsx → node`，停止时 systemd 默认向整个 cgroup 发送 SIGTERM，能够覆盖整棵树。

**`Restart=always` + `StartLimitIntervalSec=0`**

服务异常退出后会自动重启；关闭启动频率限制后，即使短时间内多次失败也会持续重试。代价是崩溃循环会持续写日志。

**日志追加到文件**

`StandardOutput=append:` 与 `StandardError=append:` 把应用输出写入 `/da04/webser/logs/pro/tangyou_uistan_0.log`。当前未配置文件轮转，磁盘占用需要另行关注。

**cgroup 与 `system.slice`**

unit 启动后位于 `/system.slice/tangyou_uistan.service`。它与 SSH 会话的 `session-*.scope` 分离，因此登录会话结束不会带走服务。

**没有显式 `RequiresMountsFor`**

当前 unit 没有写数据盘依赖。systemd 通常会为 `WorkingDirectory` 自动添加挂载依赖；若新机器的 `/da04` 挂载较慢，也可以在 `[Unit]` 中显式加入：

```ini
RequiresMountsFor=/da04/webser/sour/pro/tangyou_uistan_0
```

加入后需要重新 `daemon-reload` 与 `restart`，并重新验收。

**没有资源配置与沙箱**

当前 unit 没有 `MemoryMax`、`TasksMax`、`NoNewPrivileges`、`ProtectSystem` 等选项。它们属于加固项，加入前需要确认不会破坏 npm、tsx、Vite 与 esbuild 的运行时行为。

## 6. 安装、启动与首次核验

### 6.1 写入 unit

```bash
sudo tee /etc/systemd/system/tangyou_uistan.service > /dev/null <<'EOF'
[Unit]
Description=tangyou_uistan (npm run dev)
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=0

[Service]
Type=simple
User=webser
WorkingDirectory=/da04/webser/sour/pro/tangyou_uistan_0
ExecStart=/usr/bin/npm run dev
Restart=always
RestartSec=3
TimeoutStopSec=10
StandardOutput=append:/da04/webser/logs/pro/tangyou_uistan_0.log
StandardError=append:/da04/webser/logs/pro/tangyou_uistan_0.log

[Install]
WantedBy=multi-user.target
EOF
```

### 6.2 静态校验

```bash
sudo systemd-analyze verify /etc/systemd/system/tangyou_uistan.service
```

无输出或仅有可忽略的提示，表示 unit 语法与基本语义通过。

### 6.3 重载并启用

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now tangyou_uistan
```

### 6.4 首次检查

```bash
systemctl status tangyou_uistan --no-pager
curl -sS -m 5 http://127.0.0.1:9002/api/health; echo
curl -sS -m 5 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9002/styles/app.css
tail -8 /da04/webser/logs/pro/tangyou_uistan_0.log
```

预期形态：

- `Active: active (running)`
- `Main PID` 存在
- `CGroup: /system.slice/tangyou_uistan.service`
- 健康端点返回 `"ok":true`、`"configured":true`
- `/styles/app.css` 返回 HTTP 200
- 日志出现 `Server running on http://0.0.0.0:9002`

健康端点参考返回：

```json
{"ok":true,"configured":true,"model":"gemini-4-hydrogen","fastModel":"gemini-3.1-flash-lite","visionModel":"gemini-4-hydrogen","transcribeModel":"gemini-3.5-transcribe","customBaseUrl":false}
```

## 7. 验收与故障排查

### 7.1 六项验收

| 验收项 | 命令 | 预期 |
| --- | --- | --- |
| 进程状态 | `systemctl status tangyou_uistan --no-pager` | `active (running)`，`Main PID` 存在 |
| cgroup 归属 | 同上 | `CGroup: /system.slice/tangyou_uistan.service` |
| 业务健康 | `curl -sS -m 5 http://127.0.0.1:9002/api/health` | `ok:true`、`configured:true` |
| 断连存活 | 退出 SSH，等待，重连后再查 | `Main PID` 不变，health 正常 |
| 受控重启 | `sudo systemctl restart tangyou_uistan` | PID 变化，health 恢复 |
| 开机自启 | `systemctl is-enabled tangyou_uistan` | `enabled`；必要时重启机器验证 |

实际 reboot 与浏览器冒烟属于容易省略的两项，复现或迁移时值得一并补齐。每次具体的验收结果属于时间点事实，记录在《历史迭代阶段/》对应归档中。

### 7.2 常见故障与判读

| 现象 | 可能原因 | 判读与处理 |
| --- | --- | --- |
| `status=216/GROUP` | `Group=` 指向不存在的组 | 检查 unit 是否写了 `Group=webser`；用 `id webser` 看主组；当前形态省略 `Group=` |
| `status=217/USER` | `User=` 用户不存在 | `getent passwd webser`；必要时创建用户 |
| `status=200/CHDIR` | 工作目录不存在或不可访问 | `ls -ld /da04/webser/sour/pro/tangyou_uistan_0`；检查挂载与权限 |
| `status=203/EXEC` | `/usr/bin/npm` 不存在或不可执行 | `ls -l /usr/bin/npm`；`which node`；检查 Node 安装 |
| 启动报 `EADDRINUSE` | 9002 已被占用 | `ss -ltnp \| grep 9002`；停止旧的手工进程或另一份 unit |
| 进程 active，但 health 返回 `configured:false` | `.env.local` 缺失或 `GEMINI_API_KEY` 为空 | 检查 `.env.local` 路径、权限与字段；重启服务 |
| 进程 active，但 health 连接失败 | 端口不是 9002，或应用启动报错 | 看日志末尾；检查 `PORT`；`ss -ltnp` |
| 日志文件写入失败 | 目录不存在或属主不对 | `ls -ld /da04/webser/logs/pro`；`chown -R webser:webgp` |
| 页面字体或卡片样式异常，但 Tailwind 仍在 | 工作树缺少 `public/styles/app.css`，或 `index.html` 未引入该样式表 | `ls public/styles/app.css`；`curl -sS -m 5 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9002/styles/app.css` 应为 200 |
| 服务反复重启 | 应用启动错误或配置缺失 | `systemctl status` 看 `Result`/`ExecMainStatus`；`journalctl -u tangyou_uistan`；看应用日志 |
| SSH 断开后服务消失 | cgroup 仍挂在 `session-*.scope` | `systemctl status` 看 `CGroup`；确认启用的是 system unit |
| `code=killed, status=9/KILL` | 被 SIGKILL | 查 OOM、外部 kill、cgroup 清理 |
| `code=killed, status=15/TERM` | 被 SIGTERM | 查停止流程、外部脚本、会话清理 |
| `status=137` | 128+9，SIGKILL | 同上 |
| `status=143` | 128+15，SIGTERM | 同上 |
| `status=129` | 128+1，SIGHUP | 会话挂断、终端关闭 |

### 7.3 常用诊断命令

```bash
systemctl status tangyou_uistan --no-pager
systemctl cat tangyou_uistan
systemctl show tangyou_uistan -p ActiveState -p SubState -p MainPID -p Result -p ExecMainStatus

```

## 8. 日常运维

| 操作 | 命令 |
| --- | --- |
| 查看状态 | `systemctl status tangyou_uistan --no-pager` |
| 查看最终配置 | `systemctl cat tangyou_uistan` |
| 重启 | `sudo systemctl restart tangyou_uistan` |
| 停止 | `sudo systemctl stop tangyou_uistan` |
| 启动 | `sudo systemctl start tangyou_uistan` |
| 开机自启状态 | `systemctl is-enabled tangyou_uistan` |
| 应用日志 | `tail -f /da04/webser/logs/pro/tangyou_uistan_0.log` |
| unit 生命周期日志 | `sudo journalctl -u tangyou_uistan -f` |
| 端口检查 | `ss -ltnp \| grep 9002` |

代码与依赖变更：

- 前端文件改动由 Vite middleware 热更新，通常不需要重启。`public/styles/app.css` 变更后刷新浏览器即可确认；若样式未更新，再重启一次服务。
- `server.ts`、`server/*.ts` 等后端改动需要 `sudo systemctl restart tangyou_uistan`。
- 依赖变更后，在项目目录执行 `sudo -H -u webser npm ci --prefer-offline --no-audit --no-fund`，再重启服务。
- 回退时恢复代码或 unit 副本，再 `daemon-reload` 与 `restart`，并按第 7 节重新验收。

手工 `nohup` 实例会与 systemd 争用 9002 端口；当前唯一托管入口是 `tangyou_uistan.service`。pid 文件不再作为服务状态依据，服务状态以 `systemctl` 为准。

日志文件采用追加写入，当前未配置文件轮转。长期运行时，磁盘占用需要定期查看：

```bash
df -h /da04
ls -lh /da04/webser/logs/pro/tangyou_uistan_0.log
```

## 9. 当前形态与已知边界

| 项 | 当前形态 | 影响与复现注意点 |
| --- | --- | --- |
| 运行模式 | `npm run dev`（Vite middleware） | 常驻 Vite 开发服务器；生产构建未启用 |
| 日志轮转 | 未配置 | `append:` 文件持续增长，需要关注磁盘 |
| 挂载依赖 | unit 未显式 `RequiresMountsFor` | 依赖 systemd 对 `WorkingDirectory` 的自动挂载依赖；必要时可显式加入 |
| unit 仓库源 | 当前仅 `/etc/systemd/system` 一份 | 新机器复现可直接使用本文档第 5 节全文 |
| Node 版本 | 系统级 `/usr/bin/node`，实际版本以 `/usr/bin/node -v` 为准 | 与 `.nvmrc` 是否一致需核对；systemd 不读取 `.bash_profile` 的 nvm |
| 资源限制 | 未配置 | 无 `MemoryMax`、`CPUQuota`、`TasksMax`、`LimitNOFILE` |
| 沙箱 | 未配置 | 无 `NoNewPrivileges`、`ProtectSystem` 等 |
| `.env.local` 权限 | 以第 4.3 节为准 | 复现时确认 600、属主 `webser:webgp` |
| reboot 验证 | `is-enabled` 为 `enabled` 不等于已实际重启验证 | 复现时可在第 10 节补齐 |
| 迁移后浏览器冒烟 | health 通过不等于页面可用 | 复现时可在第 10 节补齐 |
| 反向代理/TLS/DNS | 不在本文范围 | 由上层设施负责 |
| AI Studio 预览环境 | 不在本文范围 | 平台托管，与本 unit 无关 |

负面清单：

- 不引入 pm2 或其他 supervisor，避免双重托管。
- 不把 `GEMINI_API_KEY` 写入 unit 文件。
- 不以 root 运行本服务。
- 不在未重新验收的情况下一次性开启全部沙箱选项。
- 不在同一端口上保留第二个手工启动的实例。
